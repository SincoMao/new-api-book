## 二、认证机制（`middleware/auth.go:352-483` TokenAuth）
统一归一化多种客户端鉴权头到一个 newapi 令牌 key：
1. **Anthropic风格**：路径含/v1/messages或/v1/models时，读`x-api-key`头改写为`Authorization: Bearer`(auth.go:370-375)——**Claude Code 用 ANTHROPIC_API_KEY 直连的关键**
2. **Gemini风格**：路径以/v1beta/models等开头时，读`?key=`或`x-goog-api-key`改写Bearer(auth.go:377-389)——**Gemini SDK 用 ?key= 直连的关键**
3. **OpenAI风格**：标准`Authorization: Bearer`(auth.go:390-394)
4. **WebSocket Realtime**：从`Sec-WebSocket-Protocol: openai-insecure-api-key.<key>`提取(auth.go:355-368)
5. **Midjourney**：`mj-api-secret`头兜底(auth.go:395-402)

令牌格式解析(auth.go:404-407)：去可选`sk-`前缀按`-`切分，第一段是令牌key。管理员可`key-channelId`指定渠道(SetupContextForToken auth.go:505-513，普通用户禁止)。**sk-前缀可有可无**，令牌跨端点复用。校验链：ValidateUserToken→IP白名单→用户启用→分组与令牌模型限制。

## 三、★关键判定：/v1/messages 与 /v1beta 是否原生无损直通

**结论先行**：
- `/v1/messages` 走向由**命中的渠道类型**决定，而非请求格式：
  - 命中 **Anthropic渠道(14)** → **原生无损直通**(Claude进Claude出)
  - 命中 **OpenAI/其它渠道** → **协议转换**(Claude→OpenAI)，有损
- `/v1beta` 同理：命中 **Gemini渠道(24)** → 原生直通；命中OpenAI → Gemini→OpenAI转换
- **两层"增强无损"开关**：全局 PassThroughRequestEnabled 与渠道 PassThroughBodyEnabled，开则连解析/重序列化都跳过，直接转原始字节=最彻底纯透传

### 3.1 代码证据链(Claude路径)
1. 路由/v1/messages→Relay(RelayFormatClaude)(relay-router.go:88)
2. controller.Relay按relayFormat分发：RelayFormatClaude→relay.ClaudeHelper(controller/relay.go:216-217)
3. ClaudeHelper调GetAdaptor(info.ApiType)(claude_handler.go:44)。info.ApiType由**渠道类型**经ChannelType2APIType(relay_info.go:200、api_type.go:10-11：Anthropic→APITypeAnthropic)
4. GetAdaptor(APITypeAnthropic)返回claude.Adaptor(relay_adaptor.go:58-59)
5. **claude.Adaptor.ConvertClaudeRequest原样返回**`return request, nil`(claude/adaptor.go:28-30)——**不转协议**。URL={baseUrl}/v1/messages(adaptor.go:45-46)，头设x-api-key+anthropic-version(adaptor.go:83-93)，DoResponse置FinalRequestRelayFormat=Claude(adaptor.go:125)。**端到端不转换，原生直通**
6. 对照：渠道是OpenAI类型→GetAdaptor返回openai.Adaptor，其ConvertClaudeRequest调service.ConvertRequest(...,RelayFormatOpenAI,...)**把Claude转OpenAI**(openai/adaptor.go:56-90)，且GetRequestURL改打/v1/chat/completions(adaptor.go:174-178)。**有损转换路径**

### 3.2 两层无损增强开关(claude_handler.go:135-198)
- **纯字节透传**(最彻底)：全局PassThroughRequestEnabled(默认false,global.go:36,43)或渠道PassThroughBodyEnabled为真→requestBody=ReaderOnly(storage)转发原始体，**跳过ConvertClaudeRequest/RemoveDisabledFields/ApplyParamOverride**(claude_handler.go:157-163)。Gemini同理(gemini_handler.go:139-144)
- **否则(默认)**：走ConvertClaudeRequest→Marshal→RemoveDisabledFields→ApplyParamOverride(claude_handler.go:165-198)。对Anthropic渠道仍Claude协议(无损语义)，但字节级因重序列化/裁剪/注入略有差异——**语义无损、字节非完全一致**。严格字节透传须开PassThrough
- **需警惕的"自动转换"开关**：ChatCompletionsToResponsesPolicy(默认Enabled:false,global.go:38,48-51)。若开且命中→ClaudeHelper先把Claude转OpenAI再走Responses(claude_handler.go:135-154、to_oai_responses_policy.go:8-22)。**做无损直通时必须确认此策略关闭**

### 3.3 Gemini路径(/v1beta)
1. 路由/v1beta/models/*path→Relay(RelayFormatGemini)(relay-router.go:197)→geminiRelayHandler→GeminiHelper(controller/relay.go:58-66,218-219)
2. Gemini渠道下gemini.Adaptor.ConvertGeminiRequest仅轻量规整(首条role默认user、YouTube mime补全)**原样返回**(gemini/adaptor.go:26-44)。URL按IsStream重建:generateContent或:streamGenerateContent?alt=sse(adaptor.go:166-173)。头设x-goog-api-key(adaptor.go:176-180)。**原生直通**
3. 对照：OpenAI渠道下openai.Adaptor.ConvertGeminiRequest把Gemini转OpenAI(openai/adaptor.go:44-54)
4. 流式判定：GeminiChatRequest.IsStream看?alt=sse或streamGenerateContent(dto/gemini.go:111-121)；Claude流式看body stream字段(dto/claude.go:361-366)

### 3.4 小结判定表
| 请求端点 | 命中渠道类型 | 行为 | 无损等级 |
|---|---|---|---|
| /v1/messages | Anthropic(14) | Claude原生直通 | 语义无损；开PassThrough则字节无损 |
| /v1/messages | OpenAI(1)/其它 | Claude→OpenAI转换 | 有损 |
| /v1beta/models/* | Gemini(24) | Gemini原生直通 | 语义无损；开PassThrough则字节无损 |
| /v1beta/models/* | OpenAI(1)/其它 | Gemini→OpenAI转换 | 有损 |

**核心结论**：要"客户端→newapi→原生上游"无损转发，**必须让请求格式与渠道类型匹配**(Claude客户端配Anthropic渠道、Gemini客户端配Gemini渠道)，建议对极致透传渠道开PassThroughBodyEnabled(渠道)或全局PassThroughRequestEnabled，同时确保ChatCompletionsToResponsesPolicy关闭。

## 四、客户端对接具体配置

### 4.1 Claude Code(Anthropic官方CLI)
走Anthropic Messages协议，向ANTHROPIC_BASE_URL拼接/v1/messages。newapi已注册/v1/messages且TokenAuth接受x-api-key与Bearer。
```
ANTHROPIC_BASE_URL=https://<newapi-host>        # 不带/v1，Claude Code自拼/v1/messages
ANTHROPIC_AUTH_TOKEN=<newapi-令牌>              # 走Authorization: Bearer(推荐)
# 或 ANTHROPIC_API_KEY=<newapi-令牌>            # 走x-api-key，newapi同样接受
ANTHROPIC_MODEL=claude-sonnet-4-5              # 可选默认模型
```
要点：
- 必须指向**绑定Anthropic类型渠道(14)**且模型名在白名单的令牌；否则落OpenAI渠道触发转换(有损)
- 流式SSE完整支持(ClaudeStreamHandler relay-claude.go:174)
- **/v1/messages/count_tokens未实现**：newapi未注册→NoRoute→RelayNotFound返回404(web-router.go:29-37、relay.go:459；全仓无count_tokens路由)。Claude Code的token预估收到404通常被SDK优雅降级(不影响对话)，但需提示避免误判
- 模型名用官方名；需思考模型支持-thinking后缀(claude_handler.go:76-108)，纯透传建议客户端直接发原生thinking字段

### 4.2 Cursor
走OpenAI兼容(/v1/chat/completions)。Settings→Models→填OpenAI API Key+打开"Override OpenAI Base URL"开关填base URL。
```
OpenAI API Key = <newapi-令牌>
Override OpenAI Base URL = https://<newapi-host>     # Cursor自拼/v1/chat/completions；若404改试https://<newapi-host>/v1
```
要点：模型名与渠道一致并在Cursor models列表手动添加；2025该开关有已知bug(自动重开、覆盖后模型不可用)，异常时先关Override用默认模型验证连通，必要时删Key重启Cursor重配；Cursor只走OpenAI协议，配OpenAI兼容渠道。

### 4.3 通用OpenAI兼容客户端(OpenClaw/Hermes/Cherry Studio/ChatBox/LangChain/OpenAI SDK)
```
base_url = https://<newapi-host>/v1
api_key  = <newapi-令牌>
```
- OpenAI SDK：OPENAI_BASE_URL=https://<host>/v1、OPENAI_API_KEY=<token>
- 若客户端是Anthropic协议(部分Claw/Cline变体、Claude SDK)→改用4.1指向/v1/messages
- **OpenClaw/Hermes若实为Claude协议按4.1配Anthropic渠道；若OpenAI协议按本节配。说明书应给"先判定客户端协议族→再选端点与渠道类型"决策树，不逐客户端硬编码(这两名称非标准、易变)**

### 4.4 Gemini原生客户端(Google AI SDK)
```
base_url = https://<newapi-host>           # SDK自拼/v1beta/models/...:generateContent
api_key  = <newapi-令牌>                    # ?key=或x-goog-api-key，newapi接受(auth.go:377-389)
```
须配Gemini渠道(24)走原生直通。

## 五、第11章必须覆盖要点（12条）
1. **协议族决策树**：先判客户端OpenAI/Anthropic/Gemini协议→再选端点与匹配渠道类型(无损前提)
2. **渠道类型必须与请求协议匹配**：Claude客户端→Anthropic(14)、Gemini→Gemini(24)、OpenAI→OpenAI(1)；错配触发转换(有损)，附三章证据
3. **三类无损等级**：(a)协议匹配=语义无损；(b)开PassThrough=字节无损纯透传；(c)ChatCompletionsToResponsesPolicy必须关闭
4. **base_url拼接规则**：Anthropic/Gemini客户端填主机根(自拼/v1、/v1beta)；OpenAI客户端填/v1。"404就加/去/v1"排查法
5. **鉴权头归一化**：同时接受Bearer/x-api-key/?key=/x-goog-api-key/Sec-WebSocket-Protocol/mj-api-secret；sk-前缀可有可无；令牌跨端点复用
6. **令牌与渠道绑定**：令牌→分组→渠道；端点不与令牌直绑；key-channelId指定渠道测试
7. **Claude Code专项**：ANTHROPIC_BASE_URL/AUTH_TOKEN/API_KEY写法、流式支持、模型名清单、count_tokens未实现(404)缺口
8. **Cursor专项**：Override OpenAI Base URL、模型名手动添加、2025已知bug排查
9. **模型名映射**：客户端模型名须在渠道列表；改名用ModelMapping(但改UpstreamModelName影响计费/URL，无损慎用)
10. **关闭破坏纯透传的"智能"功能清单**：ChatCompletionsToResponsesPolicy、自动补stream_options、Thinking后缀、SystemPrompt注入、ParamOverride、RemoveDisabledFields、敏感词、重试/限流——逐项给无损模式关闭指引
11. **重试与多渠道副作用**：默认按RetryTimes跨渠道重试(relay.go:191-237)，一次请求可能命中多上游；对账需知悉，必要时key-channelId锁定
12. **连通性验证与排错**：/v1/models(带协议头)验证；curl直打三核心端点最小示例；404→路由、401→令牌/头归一化、有损→渠道类型与转换开关
