# 第 10 章 · 安全

> 本章目标：把生产环境的安全配到位。每节先讲"是什么/为什么"，再给"怎么做 + 避坑"，末尾有从零加固一台 new-api 的端到端实战。
>
> 安全术语较多，首次出现都会给大白话定义。

---

## 10.1 登录会话

### SESSION_SECRET（鉴权签名密钥）
newapi 用 `SESSION_SECRET` 给登录会话/Cookie 签名。它的行为有点反直觉，务必记清（`common/init.go:50-59`）：

- **设为字面量 `random_string`** → 触发 `log.Fatal` **拒绝启动**（提示你改成真正的随机串）。不是"会话失效"，是直接起不来。
- **完全未设置** → 默认生成一个随机 UUID（`common/constants.go:35`），**每次启动都变** → 单机重启会话全失效；**多节点必然不一致**（节点 A 签的会话到节点 B 校验不过）。

→ **结论**：生产**必须显式配置一个固定的强随机值**，且**多节点全相同**。生成：`openssl rand -hex 32`。

### 会话限制（防撞库/共享账号，`common/init.go`）
撞库=用泄露的密码字典批量尝试登录。这些限制抬高攻击成本：

| 变量 | 默认 | 为什么这么设 |
|---|---|---|
| `USER_SESSION_ACTIVE_LIMIT` | 50 | 正常人不会同时在 50 台设备登录，超此多为撞库/共享账号 |
| `USER_SESSION_ISSUANCE_LIMIT` | 100 | 签发窗口内可创建会话总数（含已撤销） |
| `USER_SESSION_ISSUANCE_WINDOW_SECONDS` | 86400 | 签发计数窗口（1 天） |
| `USER_SESSION_REVOKED_RETENTION_DAYS` | 7 | 撤销会话保留几天（审计+签发计数） |
| `USER_SESSION_HOURLY_ALERT_THRESHOLD` | 5000 | 全局每小时签发告警阈值——**只告警不拒绝**；看到告警去查登录日志的异常 IP/用户 |

会话校验以**数据库为权威**；Redis 仅短期缓存（TTL 跟随 `SYNC_FREQUENCY`，默认 60 秒）。多节点共享 Redis 时撤销即时传播；独立 Redis 有有界陈旧窗口。

## 10.2 多因素与第三方登录

- **Passkey / WebAuthn**：个人设置里绑定硬件密钥或设备 Passkey（基于公钥的无密码强认证，防钓鱼）。**最推荐**。
- **2FA（TOTP）**：基于时间的一次性密码（Google Authenticator 类 App 扫码）。
- **OAuth 第三方登录**：GitHub、Discord、LinuxDO、Telegram、**微信（WeChat，`controller/wechat.go`）**。
- **自定义 OIDC**（OIDC=OpenID Connect，一种标准化的单点登录协议）：Root 在系统设置填 **OIDC Discovery URL**（一个自动发现登录端点的配置地址），newapi 自动发现并对接你的企业 SSO。
- 注册：账号密码 + 邮箱验证码，或上述 OAuth。

## 10.3 反向代理与 HTTPS

### 背景：为什么反代会丢真实 IP
newapi 跑在 Nginx 等反代后面时，到达 newapi 的请求 IP **全是 Nginx 的 IP**，真实客户端 IP 藏在 `X-Forwarded-For` 头里。但 newapi 只对**它信任的代理**传来的 `X-Forwarded-For` 才采信——这就是 `TRUSTED_PROXIES` 的作用。

- **CIDR**（无类别域间路由，一种表示 IP 范围的写法，如 `172.20.0.0/16` 表示 172.20.x.x 这一整段）。
- `TRUSTED_PROXIES` 三种模式（`trusted_proxies.go`）：
  - 留空（默认）：信任回环 + RFC1918（私有网段，如 10./172.16./192.168.）+ IPv6 ULA，启动告警。
  - `none`：严格模式，不信任任何代理（直接对外部署时用）。
  - 显式列表（如 `172.20.0.0/16`）：完全替代默认值。
- 配错后果：日志/限流看到的都是 Nginx IP，定位不到真实用户。

### HTTPS 与 Cookie 安全
- **Secure Cookie**：仅 HTTPS 下才发送的 Cookie（防止 HTTP 明文链路被窃取）。
- **Origin**：请求来源的"协议+域名+端口"（如 `https://api.example.com`）。
- `SESSION_COOKIE_SECURE=true`：启用 Secure Cookie + 对 refresh/logout 做**严格 Origin 校验**（防跨站）。
- `SESSION_COOKIE_TRUSTED_URL`：Secure 模式**必填**，精确 HTTPS Origin（逗号分隔多个，**不支持通配/路径**）。

## 10.4 限流与防滥用

多层限流（第 7 章 7.5 详述）：API 360/180s、Web 120/180s、关键操作 20/1200s、模型请求限流（按用户 ID，可分组覆盖 `[总请求,成功请求]`）。共享 Redis 时额度跨节点；独立 Redis 各算各的（总额度最坏=单节点阈值×节点数）。

## 10.5 密钥与权限安全

### 渠道密钥保护
上游 Key 只存在渠道，客户端永远拿不到（用令牌代替）。

**查看渠道 Key 的真实门槛**（`router/channel-router.go:23-29`）：需 **Root 身份**（`RootAuth`）+ **安全验证**（`SecureVerificationRequired`，即 2FA/Passkey 二次验证，scope=`channel.key.read`，`middleware/secure_verification.go`），并记审计。

> ⚠️ **查看 Key ≠ ChannelSensitiveWrite 权限**：`ChannelSensitiveWrite`（管理员可被授予）管的是"改 Key/改 base_url/改 ParamOverride·HeaderOverride"等**敏感写**（`service/authz/resources_channel.go:44-48`）；而**查看完整 Key 只有 Root 能做**（Admin 即使有 ChannelSensitiveWrite 也无权查看）。两者是不同机制，别混淆。

### 渠道权限分级（`service/authz/resources_channel.go`）
代码层定义 5 个权限：`ChannelRead`（只读）/ `ChannelOperate`（测试/状态）/ `ChannelWrite`（普通写）/ `ChannelSensitiveWrite`（敏感写）/ `ChannelSecretView`（为查看密钥预留，当前未挂载路由，因 GetChannelKey 走更严的 RootAuth）。本书"三级权限"指常用的 ChannelSensitiveWrite/ChannelWrite/ChannelOperate。

### CRYPTO_SECRET（缓存键 HMAC 密钥）
先理解为什么需要它：newapi 把令牌缓存等数据存 Redis 时，要用一个"键"去取。直接用原始键可能被猜到或冲突，于是用 **HMAC**（一种带密钥的哈希算法）把原始键"混梳"成一个哈希键。`CRYPTO_SECRET` 就是这把混梳密钥（`common/crypto.go:17-21`，HMAC-SHA256；默认跟随 `SESSION_SECRET`）。

→ **换了它会发生什么**：旧的哈希键对不上 → 缓存未命中 → 回数据库重取（缓存自然重建）。**不会丢业务数据，不是加密密钥**。但多节点共享 Redis 时必须全节点一致，否则节点间哈希键对不上。

## 10.6 生产安全清单（可执行）

| 项 | 怎么做（可复制） |
|---|---|
| 改默认密码 | 数据库/Redis 改强密码；管理员首访用初始化向导设密码（第 3 章） |
| `SESSION_SECRET` | `SESSION_SECRET=$(openssl rand -hex 32)` 生成；写入 docker-compose 的 `environment`，多节点用同一值 |
| `CRYPTO_SECRET` | 共享 Redis 时同样固定一致（可复用 SESSION_SECRET） |
| 反代 `TRUSTED_PROXIES` | docker-compose 里 `- TRUSTED_PROXIES=172.20.0.0/16`（你的 Docker 网段）；对外直连用 `none` |
| HTTPS | `- SESSION_COOKIE_SECURE=true` + `- SESSION_COOKIE_TRUSTED_URL=https://api.example.com` |
| 管理员强认证 | 个人设置 → 绑定 Passkey/WebAuthn；开启 2FA |
| 限流 | 系统设置→运营设置，按场景配 API/分组/模型限流 |

## 10.7 ★实战：从零加固一台 new-api

目标：把一台对外暴露的 new-api 加固到生产可用。

1. **生成密钥**：
   ```bash
   openssl rand -hex 32   # 得到 SESSION_SECRET 值，记下
   ```
2. **docker-compose 关键片段**：
   ```yaml
   environment:
     - SESSION_SECRET=<上一步的值>          # 固定！多节点同值
     - CRYPTO_SECRET=<同上或另生成一个>      # 共享 Redis 时固定
     - TRUSTED_PROXIES=172.20.0.0/16        # 你的反代/Docker 网段
     - SESSION_COOKIE_SECURE=true
     - SESSION_COOKIE_TRUSTED_URL=https://api.example.com
     - SQL_DSN=postgresql://root:强密码@postgres:5432/new-api
     - REDIS_CONN_STRING=redis://:强密码@redis:6379
   ```
3. **启动 + 初始化向导**设管理员密码（第 3 章）。
4. **管理员强认证**：登录 → 个人设置 → 绑定 Passkey；开 2FA。
5. **限流**：系统设置→运营设置，按用户量配 API/分组限流。
6. **验证**：
   - `curl -I https://api.example.com/api/status` 走 HTTPS 正常。
   - 日志里能看到客户端**真实 IP**（说明 `TRUSTED_PROXIES` 配对；若全是反代 IP 说明配错）。
   - 非 Root 管理员尝试查看渠道 Key 被拒（说明权限隔离生效）。
   - 重启容器后会话不丢（说明 SESSION_SECRET 固定生效）。

## 10.8 本章小结

- **SESSION_SECRET**：`random_string` 字面量会拒绝启动；未设置默认随机 UUID（多节点不一致）→ 生产必须固定强随机、多节点同值。
- 多因素：**Passkey/WebAuthn 最推荐**；OAuth 含微信；自定义 OIDC 接企业 SSO。
- 反代配 `TRUSTED_PROXIES` 还原真实 IP；HTTPS 配 `SESSION_COOKIE_SECURE`+`TRUSTED_URL`。
- **查看渠道 Key 需 Root + 安全校验（2FA/Passkey）**，非 ChannelSensitiveWrite；渠道权限 5 级（常用三级）。
- **CRYPTO_SECRET 是缓存键 HMAC 密钥**（非加密密钥），换了只触发缓存重建。
