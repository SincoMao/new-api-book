# 第 2 章 · 技术架构全景

> 本章目标：给你一张 new-api 的"技术地图"。读完你知道代码分哪几层、各层管什么、一次请求从进来到出去经过哪些关卡、以及"端点—协议—渠道"如何对应——这是理解后续所有章节（尤其第 5 章无损原理）的地基。
>
> 本章只画地图，不挖细节。每个点的深挖在对应章节。

---

## 2.1 一张图看懂分层架构

new-api 后端是经典的分层结构（来自项目自带 `AGENTS.md`）：

```
HTTP 请求
   │
   ▼  ① Router（路由）          router/          —— 把 URL 分发给对应处理器
   ▼  ② Middleware（中间件）    middleware/      —— 鉴权、限流、分发选渠道、CORS、日志
   ▼  ③ Controller（控制器）    controller/      —— 请求处理入口、参数校验、调度
   ▼  ④ Service（业务逻辑）     service/         —— 计费、渠道管理、格式转换等业务
   ▼  ⑤ Model（数据模型）       model/           —— GORM ORM，读写数据库
   ▼  ⑥ Relay（转发核心）       relay/           —— ★AI 请求转发与上游适配（本书主角）
            └─ relay/channel/                   —— 各上游适配器（openai/claude/gemini…）
   │
   ▼  上游 AI 服务（OpenAI/Anthropic/Gemini…）
```

辅助层：
- `setting/` —— 配置管理（倍率、模型设置、运营、系统、性能）
- `common/` —— 共享工具（JSON 封装、加密、Redis、限流、环境变量）
- `dto/` —— 数据传输对象（请求/响应结构体）
- `types/` —— 类型定义（RelayFormat、错误类型等）
- `constant/` —— 常量（渠道类型、API 类型、上下文键）
- `i18n/` `oauth/` `pkg/` —— 国际化、第三方登录、内部包

前端单独一层：`web/`（React 19 + Rsbuild），编译后 `//go:embed web/dist` 嵌进后端二进制（`main.go:41`）。

> 📖 **两个术语先说清**（全书反复用）：
> - **中间件（Middleware）**：请求链上一段段按顺序执行的"关卡"（鉴权、限流、选渠道……），可插拔。
> - **适配器（Adaptor，`relay/channel/` 下每个目录一个）**：专门对接某一个上游（OpenAI/Claude/Gemini…）的"桥"，负责把内部请求翻成上游看得懂的格式、把上游响应翻回来。

## 2.3 一次请求的完整旅程

以"客户端打 `/v1/chat/completions`"为例，一次请求要经过这些关卡（**细节在第 5 章逐行展开**，这里先建立印象）：

```
[客户端] POST /v1/chat/completions  (带 Authorization: Bearer <令牌>)
   │
   ▼ 全局中间件：CORS → 解压(Decompress) → BodyStorageCleanup(请求结束时清理体存储) → 统计
   ▼ TokenAuth          —— 验令牌、写用户/分组/额度到上下文
   ▼ ModelRequestRateLimit —— 模型级限流
   ▼ Distribute         —— 按模型+分组，从 ability 表选出渠道(优先级+权重)
   ▼ controller.Relay   —— 【首次读 body 时惰性快照进 BodyStorage】解析校验请求 → 生成 RelayInfo → 预扣费 → 重试循环
   ▼ XXXHelper(如 TextHelper) —— ★关键分叉：开 PassThrough? 
   │     ├─ 是 → 直接用原始字节当请求体(无损直通)
   │     └─ 否 → 适配器转换 → 序列化 → 字段裁剪 → 参数覆盖
   ▼ adaptor.DoRequest  —— 拼上游URL、设鉴权头、发出请求
   ▼ 上游返回响应
   ▼ adaptor.DoResponse —— 非流式:原样回写 or 重序列化; 流式:逐事件重打包SSE
   ▼ 结算计费 + 写日志
   ▼ [客户端]
```

这里有个全书最关键的机制——**BodyStorage 快照**（`common/gin.go:36` 的 `GetRequestBody`；接口定义 `common/body_storage.go:14`）：请求体在**第一次被读取时**（惰性，非中间件阶段）被完整存下一份**解压后的原始字节**，之后无论"解析校验/计费"还是"直通转发/重试"，都从这同一份只读快照重读。这就是为什么"网关要解析计费，却仍能做到无损直通"——**解析把原始字节反序列化为独立 DTO 对象，直通分支则再次从同一份只读 BodyStorage 重读原始字节；DTO 的任何改写都不会回写到 BodyStorage**，故解析/计费与直通互不污染。第 5 章会详细证明。

## 2.4 转发模型：端点 → RelayFormat → 渠道类型

回顾[前言·无损三定律](00-前言.md)：① 走对入口（客户端走原生协议端点）、② 上下游说同一种话（客户端配同类型渠道）。本节正是定律①②的根基，务必建立这张映射（综合 `router/relay-router.go` 与〔research/09〕）：

| 客户端协议 | 端点 | RelayFormat（内部格式标签） | 对应可原生(不触发跨格式转换)的上游渠道类型 |
|---|---|---|---|
| OpenAI Chat | `/v1/chat/completions` | `RelayFormatOpenAI` | OpenAI(1) / DeepSeek(43) / xAI(48) 等 OpenAI 兼容 |
| OpenAI Responses | `/v1/responses` | `RelayFormatOpenAIResponses` | OpenAI Responses 上游 |
| **原生 Claude** | `/v1/messages` | `RelayFormatClaude` | **Anthropic(14)** |
| **原生 Gemini** | `/v1beta/models/{model}:{action}` | `RelayFormatGemini` | **Gemini(24)** |
| Embedding | `/v1/embeddings` | `RelayFormatEmbedding` | 各支持向量化的上游 |
| 图像 | `/v1/images/generations` | `RelayFormatOpenAIImage` | OpenAI/Midjourney 等 |
| 音频 | `/v1/audio/*` | `RelayFormatOpenAIAudio` | OpenAI Whisper/TTS |
| 重排序 | `/v1/rerank` | `RelayFormatRerank` | Cohere/Jina |
| 实时 | `/v1/realtime`(WS) | `RelayFormatOpenAIRealtime` | OpenAI/Azure Realtime |

> 另有 `/v1/responses/compact`（Responses 压缩变体，独立 RelayFormat）、`/v1/completions`、`/v1/moderations`、`/v1/engines/:model/embeddings`、`/v1/models/*path`(Gemini 兼容入口) 等，完整端点见〔research/09〕与[附录 B](附录B-转发端点表.md)。

**无损的判定逻辑（分三种情形，对应第 4 章 4.6 无损策略三档；第 5 章给代码证据）**：

- 客户端打的**端点**决定 `RelayFormat`；`RelayFormat` + 命中的**渠道类型**决定走哪种情形：
- **① 协议匹配 + 默认配置 = 近似无损（不保证 100%）**：如 `/v1/messages`（Claude）命中 Anthropic 渠道——请求仍经 DTO 序列化往返 + 字段裁剪 + 可能的默认注入；主流字段经 RawMessage 覆盖（常见用法近似无损），但未声明/冷门字段可能丢。本质同第 4 章 (a) 档有损风险，详见第 5 章 5.5。
- **② 协议匹配 + 开 PassThrough = 请求体字节级无损**：开 `PassThroughBodyEnabled`（渠道）/ `PassThroughRequestEnabled`（全局），请求体原始字节直传。
- **③ 协议错配 = 跨格式转换（有损）**：如 `/v1/messages`（Claude）命中 OpenAI 渠道 → Claude→OpenAI 转换。

> 这就是为什么本书反复强调：**给客户端配匹配类型的渠道**（定律②）——Claude 客户端配 Anthropic 渠道、Gemini 客户端配 Gemini 渠道。错配=有损（③）；匹配但不开直通=近似无损/有损风险（①，要彻底无损须开直通）；要字节级无损开 PassThrough（②）。

## 2.5 数据与配置的存储

- **主数据库**：SQLite（默认）/ MySQL / PostgreSQL，由 `SQL_DSN` 前缀判定（`model/main.go:127-179`）。核心表：`channels`、`abilities`（渠道-模型-分组能力）、`tokens`、`users`、`logs`、`options`（配置键值）、`setups`（初始化状态）。
- **配置存储**：所有"系统设置"存在 `options` 表，按 `模块.键` 扁平存储；启动时由 ConfigManager 反射回填到内存单例（`setting/config/config.go`）。改设置走"系统设置"页或 API，重启不丢。
- **缓存**：Redis（可选）。开了 Redis 会强制开启内存缓存；不开则回退内存+数据库。
- **日志库**：可独立配置（`LOG_SQL_DSN`，如 ClickHouse），与主库分离。

## 2.6 前端与后端的关系

- 前端 `web/` 编译产物 `web/dist`，通过 `//go:embed` 嵌进后端二进制（`main.go:41`），所以你部署的是一个进程、一个端口（默认 3000）。
- 前端通过 `/api/*` 调后端管理接口，通过 `/v1/*`、`/v1beta/*` 等走转发。
- 也可分离部署（`FRONTEND_BASE_URL`）。

## 2.7 本章小结

- new-api 后端是 **Router→Middleware→Controller→Service→Model→relay/channel** 分层，外加 `setting/`、`common/`、`dto/` 等辅助层。
- **转发核心在 `relay/`**：handler 按协议分流，`channel/` 下每个目录是一个上游适配器。
- 一次请求经过：中间件鉴权/限流 → Distribute 选渠道 → Relay 主流程 → handler（PassThrough 分叉）→ adaptor 发上游 → 响应回写。
- **BodyStorage 快照**让"解析计费"与"无损直通"共用一份原始字节、互不污染。
- **端点→RelayFormat→渠道类型**的映射是无损定律①②的根基：客户端协议必须与上游渠道类型匹配，否则触发有损转换。
