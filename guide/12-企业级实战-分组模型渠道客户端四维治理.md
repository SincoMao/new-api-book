# 第 12 章 · 企业级实战：分组 × 模型 × 渠道 × 客户端编排

> 本章以一家约 200 人、多部门、多上游订阅的企业为例，系统讲透 newapi 的分组、模型、渠道、客户端四维编排——从复杂点分析、调度机制、配置操作到落地清单，一步一步给出可照做的方案。
>
> 本章是核心章，前序所有章节的结论在此汇聚。

---

## 12.1 场景

一家约 200 人的科技公司，使用 newapi 统一管理 AI 模型资源。

**组织结构**（按职能划分部门）：

| 部门 | 定位 | 典型模型需求 |
|---|---|---|
| 固件部门 | 底层固件/驱动开发，对代码质量要求极高 | **强性能模型**（glm-5.2 等），绝不降级 |
| 软件部门 | 通用软件开发，含 AI 应用小组 | 强性能模型 + 编码模型 |
| 硬件部门 | 硬件设计与验证 | 通用对话 + 文档 |
| 测试部门 | 质量保证 | 编码辅助 + 测试生成 |
| 方案 / 产品 / 市场 / 销售 / 采购 | 业务线 | 通用对话 + 文档 |
| 总经办 / 财务 / 行政 / 人事 | 职能 | 通用对话 |

**上游订阅**（多个来源）：
- GLM 国内版（bigmodel.cn，Coding Plan 提供 Anthropic + OpenAI 双端点）
- GLM 国际版（z.ai，Anthropic 端点）
- 阿里 Coding Plan（dashscope，Anthropic + OpenAI 双端点，含 glm / qwen / kimi 等多模型）
- DeepSeek（api.deepseek.com，Anthropic + OpenAI 双端点）
- 本地模型（内网部署的 Qwen）

**客户端**（多种混用）：
- Claude Code（Anthropic 协议）—— 固件/软件部门主力编码工具
- Cursor（OpenAI 协议）—— 部分开发者
- 其他 OpenAI 兼容客户端

## 12.2 复杂点分析

上述场景在落地时，核心复杂点有四个：

**复杂点一：同一模型、同一分组、不同协议客户端的请求路由**

固件部门的一个开发者，用 Claude Code（Anthropic 协议，打 `/v1/messages`）填模型 `glm-5.2` 能正常工作。但他换用 Cursor（OpenAI 协议，打 `/v1/chat/completions`）填同样的 `glm-5.2`，请求要么报错、要么在日志里看到被做了协议转换。

根因：newapi 普通渠道按 `(分组, 模型)` 选择渠道（`ability.go:93-95`），不校验渠道类型是否匹配客户端协议。当分组内只有 Anthropic 类型的 glm-5.2 渠道时，Cursor 的 OpenAI 请求命中它后，newapi 被迫做 OpenAI→Anthropic 跨协议转换（有损且易错）。

**复杂点二：同名模型跨上游冲突**

阿里 Coding Plan 和 GLM 官方都提供 `glm-5`，模型 id 完全相同。模型广场（`/v1/models`）聚合同名后，使用者和网关都无法区分当前请求路由到了哪个上游。

**复杂点三：多 key 额度冗余**

单个 Coding Plan key 有额度上限。高并发下一个 key 额度用完，希望自动切换到另一个 key 继续服务，而不是直接报错。

**复杂点四：分组与模型资源的治理**

14 个分组对应不同部门，需要清晰地控制"哪个部门能用哪些模型、计费倍率多少、配额上限多少"，且使用者无需操心这些后端配置。

## 12.3 编排原则：忠于使用者的模型选择

> **使用者在客户端填的模型 id（如 `glm-5.2`）是神圣的。newapi 的职责是忠实地把这个模型执行到位——在同名模型的多上游间做供应链冗余、按客户端协议做无损路由、在额度限额时自动切换——但绝不偷换成另一个（更弱的）模型。**

这条原则是本章所有配置设计的出发点。具体含义：

- 使用者填 `glm-5.2`，newapi 只在声明了 `glm-5.2` 的渠道间调度，所有渠道提供的都是 glm-5.2（同级同能力），只是上游供应商不同（GLM 国内 / 国际 / 阿里 CP）。
- 如果所有 glm-5.2 渠道都不可用，newapi 返回错误让使用者知晓，而非偷偷塞一个 `glm-4.5-air`（能力差很多）。
- 如需"全挂时降级到同级其他模型"（如 deepseek-v4-pro），必须管理员显式配置降级链，且向使用者明示。

## 12.4 渠道调度机制：priority / weight / 亲和 / 重试

> 要理解后续配置，必须先讲透 newapi 的渠道调度机制。以下原理基于 `model/ability.go:108-147`、`middleware/distributor.go:32-170`。

### priority（优先级）

渠道的 `Priority` 字段（越大越优先）。调度时，newapi 在 `(分组, 模型)` 匹配的渠道集合中，**只取最高 priority 的可用渠道**。

- 主渠道 priority 设高（如 10），备渠道设低（如 5），兜底最低（如 0）。
- 选择时只在最高 priority 档内挑，不会"跨档"随机。

### weight（权重，同 priority 内负载均衡）

同一 priority 档内有多个渠道时，按 weight 加权随机分配请求：

```
选中概率 = (渠道 Weight + 10) / Σ(同档所有渠道 Weight + 10)
```

- `+10` 是保底值，保证 `Weight=0` 的渠道也有被选中的机会（`ability.go:127-141`）。
- 想让某个渠道多承担流量，调高它的 weight。
- 多个 key 属于同一上游同一 priority 时，用 weight 在它们之间均衡负载。

### 渠道亲和（affinity）

`GetPreferredChannelByAffinity`（`distributor.go:104-132`）：某个用户+模型+分组最近成功使用过的渠道，如果仍可用，会被优先复用。

- 好处：减少渠道频繁切换，保持会话一致性（不同渠道的模型行为可能略有差异）。
- AdvancedCustom 渠道还会额外做 `channelSupportsRequestPath` 路径匹配（`distributor.go:175-184`），确保请求路径与渠道 route 对应。

### 重试降级（retry fallback）

请求失败时，newapi 按 `RetryTimes`（系统设置→运营设置→失败重试次数）重试。每次重试会**降级到下一 priority 档**（`ability.go:63-91` `getPriority`）：

```
第 1 次请求：priority=10 的渠道
第 1 次失败重试：priority=8 的渠道
第 2 次失败重试：priority=5 的渠道
...
```

- 这就是"主渠道挂了自动走备渠道"的实现机制。
- 重试只在本组（分组）+ 本模型的渠道间降级，不会跨组或跨模型。

### 自动禁用与恢复

- **自动禁用**（`ShouldDisableChannel` `service/channel.go:45`）：渠道持续报错（渠道级错误、特定状态码、关键词匹配）时，`AutoBan=1` 的渠道被自动禁用（`Status=3`），从 ability 表移除。
- **自动恢复**（`ShouldEnableChannel` `:67`）：被自动禁用的渠道，在后续请求成功时自动恢复（需全局 `AutomaticEnableChannelEnabled=true`）。
- **多 key 渠道**：单 key 失败只禁该 key（不影响其他 key），所有 key 被禁才禁整个渠道。

### 配置策略：主→备→兜底

对同一个模型（如 glm-5.2），多个渠道按 priority 分层：

| 角色 | priority | 上游 | 含义 |
|---|---|---|---|
| 主渠道 | 10 | GLM 国内（bigmodel.cn） | 首选：成本低、延迟好 |
| 备渠道 1 | 8 | GLM 国际（z.ai） | 主渠道不可用时走这里 |
| 备渠道 2 | 5 | 阿里 Coding Plan | 再不可用时走这里 |

**效果**：使用者填 `glm-5.2`，newapi 首选 GLM 国内；国内限额/故障 → 自动重试降级到国际版 → 再不行到阿里 CP。全程都是 glm-5.2，模型不变，只是换了供应商。如果配了多 key，单 key 限额先在多 key 间切，全部 key 耗尽才降级到下一 priority。

## 12.5 分组设计：按部门分配模型资源

### 分组映射

| 分组名 | 对应部门 | 可用模型范围 | 倍率 |
|---|---|---|---|
| `firmware` | 固件部门 | 全部强模型（glm-5.2、deepseek-v4-pro） | 1.0 |
| `software` | 软件部门 | 全部（含编码模型） | 1.0 |
| `hardware` | 硬件部门 | 通用 + 编码 | 1.0 |
| `qa` | 测试部门 | 编码 + 通用 | 1.0 |
| `business` | 方案/产品/市场/销售/采购 | 通用对话 | 0.8（折扣） |
| `staff` | 总经办/财务/行政/人事 | 通用对话 | 0.8 |
| `default` | 兜底 | 基础模型 | 1.0 |

### 操作步骤

1. **创建分组**：渠道编辑页，`Group` 字段填写分组名（逗号分隔多组）。
2. **渠道归组**：如 GLM 国内渠道填 `firmware,software,hardware,qa,default`（这些组都能用它）。
3. **令牌绑组**：用户创建令牌时选择自己的部门分组（如固件部门用户绑 `firmware`）。
4. **倍率配置**：系统设置→计费倍率→分组倍率，填 `{"firmware":1.0,"software":1.0,"business":0.8,"staff":0.8}`。
5. **配额**：用户管理→编辑用户→设置配额上限（如固件部门每人 500 万点/月）。

> ⚠️ **无损纪律**：要保证无损，同一个分组内声明了同一模型名（如 `glm-5.2`）的所有渠道，协议路由策略要一致——要么都是 AdvancedCustom 协议感知渠道（12.6），要么都是同协议普通渠道。不要混配（一个 AdvancedCustom + 一个普通 Anthropic），否则渠道选择可能命中协议不匹配的那个。

## 12.6 渠道配置：协议感知 + 同模型多上游冗余 + 多 key

这是本章核心操作。每个上游建一个 AdvancedCustom（类型 58）渠道，配双 route（Anthropic + OpenAI），实现协议感知路由；同组同模型的多渠道按 priority 分层，实现供应链冗余。

### 12.6.1 GLM 国内（bigmodel.cn）渠道

**操作步骤**：

1. 进入渠道编辑页，新建渠道。
2. 填写基本信息：
   - **名称**：`GLM 国内 glm-5.2`
   - **类型**：选 `Advanced Custom`（类型 58）
   - **Base URL**：`https://open.bigmodel.cn`
   - **密钥**：填 Coding Plan 的 key（多 key 见 12.6.5）
   - **模型**：`glm-5.2`（按需加 glm-4.7、glm-5 等）
   - **分组**：`firmware,software,hardware,qa,default`
   - **优先级**：`10`（主渠道）
   - **权重**：`10`
3. 其他设置→`advanced_custom`（JSON 编辑框），填入：

```json
{
  "advanced_routes": [
    {
      "incoming_path": "/v1/messages",
      "upstream_path": "/api/anthropic/v1/messages",
      "converter": "none",
      "models": ["glm-5.2"],
      "auth": {"type": "header", "name": "x-api-key", "value": "{api_key}"}
    },
    {
      "incoming_path": "/v1/chat/completions",
      "upstream_path": "/api/coding/paas/v4/chat/completions",
      "converter": "none",
      "models": ["glm-5.2"],
      "auth": {"type": "header", "name": "Authorization", "value": "Bearer {api_key}"}
    }
  ]
}
```

4. 设置→打开"请求体直通"开关（`pass_through_body_enabled: true`），实现请求体字节级无损。
5. 保存。

**效果**：
- Claude Code 打 `/v1/messages` → 命中 route 1 → `bigmodel.cn/api/anthropic/v1/messages`（Anthropic 原生）
- Cursor 打 `/v1/chat/completions` → 命中 route 2 → `bigmodel.cn/api/coding/paas/v4/chat/completions`（OpenAI 原生）
- 两条 route 都 `converter=none` + PassThrough → 零协议转换、请求体字节级无损。

> **anthropic-version 头**：AdvancedCustom adapter 在 `converter=none` 且 Claude 格式时会自动注入 `anthropic-version: 2023-06-01`（`advancedcustom/adaptor.go:490-507`），无需手动配置。

### 12.6.2 GLM 国际（z.ai）渠道

同上操作，差异：
- **Base URL**：`https://api.z.ai`
- **upstream_path** 的 Anthropic 端点改为 z.ai 对应路径
- **优先级**：`8`（备渠道 1）
- **分组**：加 `firmware,software,...`（同上，或只给 `firmware,software` 限制范围）

### 12.6.3 阿里 Coding Plan 渠道

同上操作，差异：
- **Base URL**：`https://coding.dashscope.aliyuncs.com`
- **Anthropic route** upstream_path：`/apps/anthropic`
- **OpenAI route** upstream_path：`/v1/chat/completions`
- **models**：Anthropic route 填 `glm-5`（阿里 CP 提供的 glm 系列），OpenAI route 填 `qwen3-coder-plus,kimi-k2.5`（非 glm 模型）
- **优先级**：`5`（备渠道 2）

> 注意：阿里 CP 的 glm 模型和 GLM 官方的 glm 模型同名问题，见 12.7 模型治理。

### 12.6.4 DeepSeek 渠道

DeepSeek 同样提供双协议端点。建一个 AdvancedCustom 渠道：
- **Anthropic route**：`/v1/messages` → `/anthropic/v1/messages`
- **OpenAI route**：`/v1/chat/completions` → `/v1/chat/completions`
- **models**：`deepseek-v4-flash,deepseek-v4-pro`
- **优先级**：`10`（作为 deepseek 模型的首选）
- **分组**：`firmware,software,hardware,qa`

### 12.6.5 多 key 配置（单渠道内冗余）

单个 Coding Plan key 额度有限，想配多 key 自动轮转：

1. 渠道编辑页，**密钥**字段填多行（每行一个 key）：

```
ghp_key1_xxxxxxxx
ghp_key2_yyyyyyyy
ghp_key3_zzzzzzzz
```

2. newapi 自动识别为多 key 模式（`ChannelInfo.IsMultiKey=true`）。
3. 选择 `MultiKeyMode`：
   - `polling`（轮询）：按顺序循环使用每个 key
   - `random`（随机）：随机选一个 key
4. 单 key 报错/限额时，自动跳到下一个 key（只禁该 key）；所有 key 都不可用才禁整个渠道。

### 12.6.6 同模型多上游冗余（供应链高可用）

对同一个模型 `glm-5.2`，建三个 AdvancedCustom 渠道（12.6.1-12.6.3），同分组同模型，priority 分层：

| 渠道 | 上游 | priority | 角色 |
|---|---|---|---|
| GLM 国内 glm-5.2 | bigmodel.cn | 10 | 主 |
| GLM 国际 glm-5.2 | z.ai | 8 | 备 1 |
| 阿里 CP glm-5 | dashscope | 5 | 备 2 |

**效果**：使用者填 `glm-5.2`，newapi 按 priority 首选 GLM 国内。国内限额（多 key 全耗尽）→ 自动禁用 → 重试降级到国际版 → 再不行到阿里 CP。**全程都是 glm-5.2 / 同级模型，使用者无感知，质量不降级。**

## 12.7 模型治理：同名冲突处理

阿里 CP 和 GLM 官方都有 `glm-5`。模型广场聚合同名后冲突。三种解法：

**方案 A（推荐）：优先级策略**

把多个同名渠道放同组，靠 `priority` 决定首选、`weight` 决定同级负载。使用者填 `glm-5`，newapi 按优先级选可用渠道——GLM 国内（priority 10）优先，限额后降级到阿里 CP（priority 5）。使用者无需关心走了哪个上游。

**方案 B：渠道模型名区分**

GLM 官方渠道 models 用 `glm-5`，阿里 CP 渠道用 `glm-5-ali`，配合 ModelMapping 把 `glm-5-ali` 映射回上游真实名 `glm-5`。想指定上游的使用者填 `glm-5-ali`；不指定的填 `glm-5` 走优先级。

**方案 C：分组隔离**

阿里 CP 的 glm 渠道只放特定分组（如 `qa`），GLM 官方放通用分组（如 `firmware,software`），靠分组避免同名渠道混在同一个选择域里。

## 12.8 客户端对接：统一入口

使用者只需记住两件事：**newapi 地址** + **模型 id**。newapi 根据客户端协议自动选择 AdvancedCustom 渠道的对应 route。

### 固件部门开发者（Claude Code + Cursor 都用）

**Claude Code**（Anthropic 协议）：
```bash
ANTHROPIC_BASE_URL=https://<newapi 地址>     # 不带 /v1
ANTHROPIC_AUTH_TOKEN=<newapi 令牌>           # 令牌绑 firmware 组
```
settings.json：
```json
{ "env": { "ANTHROPIC_BASE_URL": "https://<newapi 地址>", "ANTHROPIC_AUTH_TOKEN": "<令牌>" } }
```
模型填 `glm-5.2`。

**Cursor**（OpenAI 协议）：
```
Settings → Models → OpenAI API Key = <newapi 令牌>
Override OpenAI Base URL = https://<newapi 地址>/v1
```
模型列表手动加 `glm-5.2`。

**同一把令牌**（绑 `firmware` 组），两个客户端都能用 `glm-5.2`。newapi 根据请求路径（`/v1/messages` vs `/v1/chat/completions`）自动选 AdvancedCustom 的对应 route，零协议转换。

### 软件部门开发者

同上，令牌绑 `software` 组。可用模型范围与固件部门一致（或按需调整分组渠道归属）。

### 业务/职能部门

用通用对话即可。令牌绑 `business` 或 `staff` 组，填模型 `glm-5` 或 `qwen3-coder-plus`（视分组渠道配置）。

## 12.9 计费与成本治理

### 倍率配置

系统设置→计费倍率：
- **模型倍率**：按上游实际定价填。如 GLM Coding Plan 包月（成本可折算为低倍率），DeepSeek 按量（按官方价）。
- **分组倍率**：`{"firmware":1.0,"software":1.0,"business":0.8,"staff":0.8}`。业务/职能部门打折（或公司补贴）。

### 按部门核算

日志页按 `分组` 过滤，查看每个部门的配额消耗趋势。配合数据看板（控制台→数据看板）做可视化。

### 配额预警

用户管理→编辑用户→设置配额上限。配额接近上限时，使用者会收到余额不足提示。管理员可在日志页监控异常消耗。

## 12.10 可观测：渠道健康与成本监控

### 渠道健康度

渠道列表页显示每个渠道的：响应时间（ms）、最近测试结果、余额、状态（启用/禁用/自动禁用）。
- 响应时间持续偏高的渠道，考虑调低 priority 或 weight。
- 频繁自动禁用的渠道，排查上游稳定性。

### 请求日志

日志页每条记录包含：命中的渠道名、模型、协议路径、消耗 token、配额。用日志验证无损（渠道类型正确、模型未被意外映射、token 消耗合理——第 9 章 9.6 三法）。

### 成本看板

数据看板按时间/模型/分组/渠道维度统计用量趋势、配额消耗、调用次数。定期导出做部门成本对账。

## 12.11 完整配置清单

| 维度 | 配置 | 关键字段 |
|---|---|---|
| **分组** | 按部门建组（firmware/software/hardware/qa/business/staff/default） | 渠道 `Group` 字段；令牌绑组；分组倍率 |
| **GLM 渠道** | AdvancedCustom(58)，双 route | Anthropic route → `/api/anthropic/v1/messages`；OpenAI route → `/api/coding/paas/v4/chat/completions`；converter=none；PassThrough=true |
| **DeepSeek 渠道** | AdvancedCustom(58)，双 route | 同上模式 |
| **阿里 CP 渠道** | AdvancedCustom(58)，双 route | models 按协议分 |
| **多 key** | 密钥多行 + MultiKeyMode | polling/random；单 key 失败只禁该 key |
| **多上游冗余** | 同组同模型多渠道 + priority | 国内(10) > 国际(8) > 阿里CP(5) |
| **模型冲突** | 优先级策略 / 模型名区分 / 分组隔离 | 同名靠 priority 选可用 |
| **客户端** | 统一 URL + 模型 id | newapi 按协议路径自动路由 |
| **无损** | converter=none + PassThrough | 请求体字节级无损 |
| **质量红线** | 同模型多上游调度，绝不偷换弱模型 | 全部同名渠道不可用 → 返回错误 |

### 落地步骤（按顺序操作）

1. **建分组**：系统设置→运营设置，规划分组名与倍率。
2. **建 GLM 国内渠道**：AdvancedCustom 双 route + PassThrough + priority 10。
3. **建 GLM 国际渠道**：同上 + priority 8。
4. **建阿里 CP 渠道**：同上 + priority 5。
5. **建 DeepSeek 渠道**：同上 + priority 10（deepseek 模型的首选）。
6. **配多 key**：每个渠道密钥填多行。
7. **建令牌**：按部门绑定分组 + 模型限制。
8. **配客户端**：发 URL + 令牌给使用者，各自客户端填入。
9. **验证**：用日志确认渠道命中正确、协议无转换、token 一致。
10. **调优**：观察一周日志，按实际延迟/成功率调整 priority 和 weight。
