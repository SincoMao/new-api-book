# 第 12 章 · 企业级实战：分组 × 模型 × 渠道 × 客户端四维治理

> 本章是一个真实场景的庖丁解牛：一家约 200 人、按部门分组、订阅了多个上游（GLM 国内/国际、阿里 Coding Plan、DeepSeek、本地模型）的公司，如何用 new-api 做到——**使用者只填一个 URL 和模型 id，无论用 claude code 还是 cursor，newapi 都能按客户端协议把请求无损路由到对应上游端点，且多上游自动冗余**。
>
> 本章是核心章。前面所有章节的结论在这里汇聚成一套可落地的企业方案。

---

## 12.1 场景与四大难题

### 公司画像
- 约 200 人，分软件（SD）、硬件（HW/BIOS/BMC）、测试（SIT）、产品（PD）、项目（PM）、供应链（SCM）、人力（HR）、行政、财务、市场、客户成功（CSC）、总经办（GMO）、AI 组等。软件部下还有二级组。
- 每个部门能用哪些模型、计费倍率不同 → 用 **分组** 隔离。

### 上游订阅（多个）
- **GLM 国内版**（bigmodel.cn，Coding Plan：`/api/anthropic` + `/api/coding/paas/v4` 双端点）
- **GLM 国际版**（z.ai，`/api/anthropic`）
- **阿里 Coding Plan**（dashscope，`/apps/anthropic` + `/v1/chat/completions` 双端点；含 glm / qwen / kimi / MiniMax）
- **DeepSeek**（`api.deepseek.com`，`/anthropic` + 默认 OpenAI 双端点）
- **本地模型**（内网 vLLM，OpenAI 协议）

### 四大难题（真实踩过的坑）
1. **同模型多协议客户端，渠道总出错**：BIOS 组的开发者，用 claude code（Anthropic 协议）填 `glm-5.2` 能用；换成 cursor（OpenAI 协议）填同样的 `glm-5.2`，日志却显示请求被"转了协议"。曾尝试给 GLM 配 OpenAI 端点渠道，结果反而让 cursor 命中 Anthropic 渠道被转换——只能删掉，问题没解决。
2. **模型 id 冲突**：阿里 Coding Plan 也有 `glm-4.7`/`glm-5`，和 GLM 官方的同名，模型广场里分不清来自哪个上游。
3. **多 key 冗余**：单个 Coding Plan key 有额度上限，一个 key 到顶就想自动切到另一个。
4. **分组治理**：14 个分组对应部门，要把"哪个部门能用哪些模型/上游"管清楚，还不能让使用者操心。

## 12.2 核心症结：普通渠道"按组+模型选，不按协议选"

第 4 章讲过渠道选择：newapi 按 `(group, model, priority, weight)` 选渠道（`ability.go:93-95`、`channel_cache.go:114-208`），**全程不看渠道类型（OpenAI/Anthropic）是否匹配客户端协议**。

于是当同一个模型 `glm-5.2` 在 BIOS 组里只有 **Anthropic 类型**渠道时：
- claude code 打 `/v1/messages`（Anthropic）→ 命中 Anthropic 渠道 → 原生直通 ✓
- cursor 打 `/v1/chat/completions`（OpenAI）→ **也命中这个 Anthropic 渠道** → newapi 被迫把 OpenAI 请求转成 Anthropic 发给上游（跨协议转换，有损且易错）✗

反过来，如果你再配一个 GLM **OpenAI 类型**渠道（同组同模型），claude code 又可能命中它被转成 OpenAI。**只要"同组+同模型"里混了两种协议类型的普通渠道，就一定有一个客户端被转换**——这是普通渠道机制的天花板。

## 12.3 总架构：用 AdvancedCustom 做"协议感知"渠道

解药是第 4 章 4.7 的 **AdvancedCustom（类型 58）**。它的路由表能**按请求路径（= 客户端协议）匹配不同 route**（`distributor.go:175-184` 的 `channelSupportsRequestPath` + `ability.go:154-194` 的路径过滤）：

```
使用者（BIOS 组，无论 claude code 还是 cursor）
   │  只填 newapi 地址 + 模型 glm-5.2
   ▼
newapi 看请求路径（协议）
   ├─ /v1/messages      (claude code, Anthropic) → route A → 上游 Anthropic 端点
   └─ /v1/chat/completions (cursor/hermes, OpenAI) → route B → 上游 OpenAI 端点
```

**一个 AdvancedCustom 渠道 = 一个上游的两种协议端点**，`converter=none`（不跨协议转换）。这样使用者无论哪个客户端、填同样 URL+模型 id，newapi 都按协议智慧路由到同协议端点，零转换。

多上游冗余：bigmodel 国内、z.ai 国际、阿里 CP 各建一个 AdvancedCustom 渠道，**同组同模型 glm-5.2**，靠 `priority`/`weight` 负载均衡 + 自动禁用实现"哪个可用、哪个不拥挤走哪个"。

## 12.4 第一维 · 分组（部门 → 模型资源）

### 分组设计（对应部门）
建议分组名用部门缩写，一眼能认：

| 分组 | 含义 | 典型可用模型 |
|---|---|---|
| SD / BIOS / BMC | 软件开发（含固件/基板） | 全部（GLM、DeepSeek、qwen-coder、本地模型） |
| SIT | 测试 | GLM、DeepSeek（coding 用） |
| PD / PM / SCM | 产品/项目/供应链 | GLM、qwen、DeepSeek |
| HR / 行政 / 财务 / CSC / GMO | 职能 | GLM、qwen、本地模型 |
| AI | AI 组（尝鲜） | 全部 + 优先级高 |
| vip / svip | 高级 | 全部 + 国际版 GLM |
| default | 默认/兜底 | GLM 聚合渠道 |

### 渠道归组
渠道 `Group` 字段填它归属的分组（逗号多组）。例如 GLM 国内 AdvancedCustom 渠道填 `BIOS,BMC,SD,AI,SIT,default`——这些组都能用它。

### 令牌绑组
用户/令牌绑定自己部门的组（如 BIOS 开发者的令牌绑 `BIOS`）。绑 `auto` 则跨组容灾（第 7 章 7.4）。

> ⚠️ **无损纪律（第 7 章 7.6）**：要保无损，BIOS 组内凡是声明了 `glm-*` 的渠道，协议路由要一致（都用 AdvancedCustom 协议感知，或都用同协议普通渠道），别混着配。

## 12.5 第二维 · 渠道（AdvancedCustom 协议感知 + 多 key）

这是本章核心。**每个上游建一个 AdvancedCustom 渠道，配双 route**。

### GLM 国内（bigmodel.cn）— 模板
- **Type**：58（AdvancedCustom）
- **BaseURL**：`https://open.bigmodel.cn`
- **Key**：GLM Coding Plan 的 key（多 key 见 12.5 末尾）
- **Models**：`glm-4.5,glm-4.5-air,glm-4.6,glm-4.7,glm-5,glm-5-turbo,glm-5.1,glm-5.2`
- **Group**：`BIOS,BMC,SD,AI,SIT,default`
- **OtherSettings → `advanced_custom.advanced_routes`**（⚠️ JSON 键是 `advanced_routes`，第 4 章 4.7）：

```json
{
  "advanced_routes": [
    {
      "incoming_path": "/v1/messages",
      "upstream_path": "/api/anthropic/v1/messages",
      "converter": "none",
      "models": ["glm-4.5","glm-4.5-air","glm-4.6","glm-4.7","glm-5","glm-5-turbo","glm-5.1","glm-5.2"],
      "auth": {"type": "header", "name": "x-api-key", "value": "{api_key}"}
    },
    {
      "incoming_path": "/v1/chat/completions",
      "upstream_path": "/api/coding/paas/v4/chat/completions",
      "converter": "none",
      "models": ["glm-4.5","glm-4.5-air","glm-4.6","glm-4.7","glm-5","glm-5-turbo","glm-5.1","glm-5.2"],
      "auth": {"type": "header", "name": "Authorization", "value": "Bearer {api_key}"}
    }
  ]
}
```

- **Setting**：开 `pass_through_body_enabled: true`（请求体字节级无损；advancedcustom 的 converter=none route 允许 PassThrough，`adaptor.go:272-274`）。
- **anthropic-version** 头：AdvancedCustom adapter 在 converter=none 且 Claude 格式时**自动补**（默认 `2023-06-01`），无需手配（第 4 章 4.7）。

**效果**：BIOS 组的开发者——
- claude code 打 `/v1/messages` → 命中 route 1 → `bigmodel.cn/api/anthropic/v1/messages`（Anthropic 原生）
- cursor/hermes 打 `/v1/chat/completions` → 命中 route 2 → `bigmodel.cn/api/coding/paas/v4/chat/completions`（OpenAI 原生）
- 两者都 `converter=none` + PassThrough → **零协议转换、请求体字节级无损**。

### GLM 国际（z.ai）
同样建一个 AdvancedCustom 渠道，BaseURL `https://api.z.ai`，route 的 upstream_path 用 `/api/anthropic/v1/messages` + z.ai 的 OpenAI 端点。Group 加 `vip,svip`（国际版通常给高级用户）。

### DeepSeek（双端点范本）
DeepSeek 也有 `/anthropic` + 默认 OpenAI 端点。建一个 AdvancedCustom 渠道：
- route 1：`/v1/messages` → `/anthropic/v1/messages`
- route 2：`/v1/chat/completions` → `/v1/chat/completions`（DeepSeek 默认 OpenAI 端点）
- models：`deepseek-v4-flash,deepseek-v4-pro`

> 你们现在用普通渠道给 DeepSeek 配了 [13]Anthropic + [14]OpenAI 两个渠道，存在和 GLM 一样的"cursor 可能命中 Anthropic 渠道被转换"风险。统一改成 AdvancedCustom 双 route 即可根治。

### 阿里 Coding Plan（双端点）
- route 1：`/v1/messages` → `https://coding.dashscope.aliyuncs.com/apps/anthropic`（GLM 系列）
- route 2：`/v1/chat/completions` → `https://coding.dashscope.aliyuncs.com/v1/chat/completions`（qwen/kimi/MiniMax）
- 注意 models 要区分：route 1 填 `glm-4.7,glm-5`，route 2 填 `qwen3-coder-plus,kimi-k2.5,...`（见 12.6 模型治理）。

### 多 key 冗余（单个渠道多个 key）
Coding Plan key 有额度上限，想"一个限额自动走另一个"：渠道 `Key` 字段**填多行**（每行一个 key），`ChannelInfo.IsMultiKey=true`，`MultiKeyMode` 选 `polling`（轮询）或 `random`（随机）。单 key 失败/限额只禁该 key，全禁才禁渠道（第 4 章 4.10）。

```
key1_xxx
key2_yyy
key3_zzz
```

> 多 key 模式下，AdvancedCustom 的 `{api_key}` 占位会替换为当前轮询选中的那个 key。

### 多上游冗余（多个渠道）
bigmodel 国内、z.ai 国际、阿里 CP 各一个 AdvancedCustom 渠道，**同组（如 BIOS）同模型（glm-5.2）**。设：
- bigmodel 国内 `priority=2`（优先）
- 阿里 CP `priority=1`
- z.ai 国际 `priority=0`（兜底）

priority 高的优先；高的限额/失败自动降级到低的（第 4 章 4.4 重试降级）。这就实现了"哪个能用走哪个、哪个不拥挤走哪个"。

## 12.6 第三维 · 模型治理（同名冲突）

阿里 CP 和 GLM 官方都有 `glm-4.7`/`glm-5`。模型广场（`/v1/models`）聚合同名，使用者填 `glm-5` 不知道走哪个上游。三种解法：

1. **优先级即策略（推荐）**：把多个同名渠道放同组，靠 `priority` 决定首选、`weight` 决定同级负载。使用者填 `glm-5`，newapi 按优先级选可用渠道——这正是你要的"哪个能用走哪个"。
2. **渠道模型名前缀**：GLM 官方渠道 models 用 `glm-5`，阿里 CP 渠道用 `glm-5-ali` + ModelMapping 映射回 `glm-5`。使用者想指定上游就填带前缀的；不指定就填 `glm-5` 走优先级。
3. **分组隔离**：把阿里 CP 的 glm 渠道只放 `SIT` 组（给特定场景），GLM 官方放通用组，靠分组避免混用。

> 你们现在阿里 CP[10] 只声明 `glm-4.7,glm-5` 且面向 SIT/SCM/GMO/AI，GLM 官方渠道声明全系列——基本是"方案 3（分组隔离）"的雏形。可继续沿这个思路。

## 12.7 第四维 · 客户端（统一入口，协议智慧路由）

使用者只需记住：**URL = newapi 地址，模型 id 填模型名**。newapi 按客户端协议自动路由（因为 AdvancedCustom 双 route）。

### claude code（Anthropic 协议）
```
ANTHROPIC_BASE_URL=https://<newapi 地址>     # 自拼 /v1/messages → route A
ANTHROPIC_AUTH_TOKEN=<newapi 令牌>           # 令牌绑 BIOS 组
# 模型填 glm-5.2（或 ANTHROPIC_MODEL=glm-5.2）
```

### cursor（OpenAI 协议）
```
Override OpenAI Base URL = https://<newapi 地址>/v1   # 自拼 /chat/completions → route B
OpenAI API Key = <newapi 令牌>                        # 同一把令牌
# 模型列表手动加 glm-5.2
```

### hermes / 其他 OpenAI 客户端
```
base_url = https://<newapi 地址>/v1
api_key  = <newapi 令牌>
模型 = glm-5.2
```

**关键**：同一个 BIOS 组的令牌，claude code 和 cursor 用的是**同一把**（令牌绑组，组内渠道决定能用的模型）。newapi 根据请求路径（`/v1/messages` vs `/v1/chat/completions`）自动选 AdvancedCustom 的对应 route，使用者完全无感。

> ⚠️ **无损保证**：route 都 `converter=none` + 渠道开 PassThrough → 请求体字节级无损直通到对应协议的上游端点（第 5 章三定律全满足）。

## 12.8 多 key 限额自动切换（深入）

- 单个 AdvancedCustom 渠道 `Key` 填多行（多 key 模式，`MultiKeyMode=polling`）→ key1 用到限额/失败 → 自动切 key2 → 全失败才禁渠道。
- 想要"限额"自动切换（而非"报错"才切）：配合渠道的 `StatusCodeMapping`，把上游"额度不足"的状态码（如 429）映射，或依赖 `AutoBan` + 多 key 的单 key 禁用机制。
- 多渠道层面：bigmodel（priority 2）→ 阿里 CP（priority 1）→ z.ai（priority 0），高优先级不可用自动降级。

## 12.9 计费按部门 + 验证

- **分组倍率**：系统设置→计费倍率，按组设（如 SD 组 1.0、HR 组 0.8）。令牌绑哪个组用哪个倍率。
- **按部门核算**：日志页按 group 过滤，看每个部门的配额消耗（第 9 章）。
- **无损验证**：BIOS 开发者用 claude code 和 cursor 各发一条 glm-5.2 → 日志看命中的渠道都是 AdvancedCustom、模型 glm-5.2、且**协议路径正确**（claude code 走 /v1/messages、cursor 走 /v1/chat/completions，无转换日志）→ 对比直连质量一致。

## 12.10 完整配置清单（一表汇总）

| 维度 | 配置 | 要点 |
|---|---|---|
| **分组** | 14 组对应部门 | 渠道 Group 填多组；令牌绑部门组 |
| **GLM 渠道** | AdvancedCustom(58) 双 route | route A `/v1/messages`→`/api/anthropic`；route B `/v1/chat/completions`→`/api/coding/paas/v4`；converter=none；PT=true |
| **DeepSeek 渠道** | AdvancedCustom 双 route | 同上模式（`/anthropic` + 默认 OpenAI） |
| **阿里 CP** | AdvancedCustom 双 route | models 按协议分（glm 走 A、qwen/kimi 走 B） |
| **多 key** | Key 多行 + MultiKeyMode | 单渠道内冗余，限额自动切 |
| **多上游冗余** | 多渠道同组同模型 + priority | 国内2 > CP1 > 国际0，可用/不拥挤优先 |
| **模型冲突** | priority 策略 / 模型名前缀 / 分组隔离 | 同名靠优先级选可用 |
| **客户端** | 统一 URL + 模型 id | newapi 按协议路径智慧路由 |
| **无损** | converter=none + PassThrough | 请求体字节级无损 |

## 一句话总结

> **用 AdvancedCustom 协议感知渠道，把"同模型多协议客户端"这个普通渠道解不开的死结，变成"一个渠道两条 route，按请求路径自动选对应协议端点"。使用者只管填 URL 和模型 id，newapi 做剩下的智慧路由——无损、多上游冗余、按部门分组治理。**

这解决了你们"分组、模型、渠道、客户端"四大难题的交汇点。其余三维（分组隔离资源、模型冲突靠优先级、多 key 冗余）都是围绕这个核心的配套。
