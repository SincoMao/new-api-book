# 第 11 章 · 客户端透明无损对接实战

> 本章是全书的**核心主线集大成**。它把前面所有章节（架构、渠道、转发原理、参数调教、令牌、验证）汇聚到一个端到端的实战：**让 claude code、cursor、openclaw、hermes 等客户端经 newapi 无损转发到原生上游，质量等同直连官方 API**。
>
> 本章是核心章，加强审查。

---

## 11.0 目标与总策略

**目标**：客户端 → newapi → 原生上游，**零质量损失**（在需要时对 GLM-5.2 等个别模型主动、可控地微调 max_tokens）。

**总策略（无损三定律落地）**：
1. **判定客户端协议族**（OpenAI / Anthropic / Gemini）→
2. **选对应原生端点**（`/v1/chat/completions` / `/v1/messages` / `/v1beta/...`）→
3. **配同类型渠道**（OpenAI 渠道 / Anthropic 渠道 / Gemini 渠道）+ **开 PassThrough**（字节级无损）。

> ⚠️ **互斥提醒**（第 5 章 5.9）：需要改 max_tokens 的模型（如 GLM-5.2）**单独建非直通渠道**用 ParamOverride，不要和直通渠道混。

## 11.1 协议族决策树

先判定你的客户端是哪种协议，再选端点与渠道类型：

```
你的客户端发什么格式的请求？
 │
 ├─ Anthropic Messages 格式（如 Claude Code、Claude SDK、部分 Cline/Claw 变体）
 │    → 端点 /v1/messages → 配 Anthropic 渠道(14)
 │
 ├─ OpenAI 兼容格式（如 Cursor、Cherry Studio、ChatBox、LangChain、OpenAI SDK、多数编码客户端）
 │    → 端点 /v1/chat/completions → 配 OpenAI 渠道(1) 或 OpenAI 兼容第三方(DeepSeek/xAI/…)
 │
 ├─ Google Gemini 格式（Google AI SDK）
 │    → 端点 /v1beta/models/{model}:{action} → 配 Gemini 渠道(24)
 │
 └─ OpenAI Responses 格式（Codex 等）
      → 端点 /v1/responses → 配支持 Responses 的上游
```

> **判不准时**：看客户端文档它"base_url 拼什么后缀"。拼 `/v1/messages` = Anthropic；拼 `/v1/chat/completions` = OpenAI；拼 `/v1beta/...` = Gemini。

## 11.2 base_url 拼接规则

不同协议客户端填的 base_url 不同（〔research/09〕）：

| 客户端协议 | base_url 填到 | 客户端自拼后缀 |
|---|---|---|
| Anthropic | **主机根** `https://<host>` | `/v1/messages` |
| OpenAI | **`/v1`** `https://<host>/v1` | `/chat/completions` |
| Gemini | **主机根** `https://<host>` | `/v1beta/models/...` |

**排查口诀**：客户端报 404 → 多半是 base_url 多/少了 `/v1`。试着加或去掉 `/v1` 再试。

## 11.3 认证头归一化（一个令牌通用）

newapi 的 `TokenAuth`（`middleware/auth.go:352-488`）会**统一归一化**多种客户端鉴权头到一个令牌 key：

- `Authorization: Bearer <token>`（OpenAI 风格）
- `x-api-key: <token>`（Anthropic 风格，`/v1/messages`）
- `?key=<token>` 或 `x-goog-api-key`（Gemini 风格，`/v1beta`）
- `Sec-WebSocket-Protocol: openai-insecure-api-key.<token>`（Realtime）

→ **令牌 key 的 `sk-` 前缀可有可无**；**一把令牌可跨端点复用**（Claude/OpenAI/Gemini 端点都能用同一把）。

## 11.4 ★Claude Code 对接（无损）

Claude Code 走 Anthropic Messages 协议，向 `ANTHROPIC_BASE_URL` 拼 `/v1/messages`。

**环境变量**（shell 导出，或写入 `~/.claude/settings.json` 的 `env`）：
```bash
ANTHROPIC_BASE_URL=https://<your-newapi-host>     # 不带 /v1，Claude Code 自拼 /v1/messages
ANTHROPIC_AUTH_TOKEN=<newapi-令牌>                # 走 Authorization: Bearer（推荐）
# 或 ANTHROPIC_API_KEY=<newapi-令牌>              # 走 x-api-key，newapi 同样接受
# ANTHROPIC_MODEL=claude-sonnet-4-5              # 可选默认模型
```

**或 `~/.claude/settings.json`**（跨平台推荐，Windows/PowerShell 小白用这个）：
```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "https://<your-newapi-host>",
    "ANTHROPIC_AUTH_TOKEN": "<newapi-令牌>"
  }
}
```

**前提配置**（前序章节已完成）：
- Anthropic 渠道（Type=14），开了 `PassThroughBodyEnabled`，`Group=default`，`Models` 含 claude 模型。
- 令牌（第 7 章 7.6）：**模型限制**只允许 claude 模型，绑 `default` 组。

**无损保证**：Claude Code 打 `/v1/messages`（`RelayFormatClaude`）→ 命中 Anthropic 渠道（类型匹配，定律②）→ PassThrough（定律③）→ **请求体字节级无损直通**到 Anthropic 上游；流式 SSE 事件内容等价。

⚠️ **已知缺口**：newapi 仅注册 `POST /v1/messages`（`relay-router.go:88`），**未注册 `/v1/messages/count_tokens`** → 落 NoRoute 返回 404（`web-router.go:29-37`）。Claude Code 的 token 预估/上下文预算调用会收到 404——**多数情况不影响对话生成**，但 token 预估会失败；个别 SDK 版本或 VS Code 扩展场景可能报错（社区有"返回 dummy 计数"的 workaround）。如需彻底消除可由网关返回 dummy 计数。

## 11.5 ★Cursor 对接

Cursor 走 OpenAI 兼容协议（`/v1/chat/completions`）。配置入口：**Settings → Models → 填 OpenAI API Key → 打开"Override OpenAI Base URL"开关 → 填 base URL**。

```
OpenAI API Key = <newapi-令牌>
Override OpenAI Base URL = https://<your-newapi-host>/v1   # ★填到 /v1！Cursor 在其后追加 /chat/completions（不会自动补 /v1）
```

要点：
- **模型名**需与 newapi 渠道里的模型名一致；在 Cursor 的 models 列表里**手动添加**这些名字。
- ⚠️ **2025 已知 bug**：该开关存在"自动重开、覆盖后模型不可用"等问题（社区多条报告）。排查：先**关闭 Override**用默认模型验证连通，再排查；必要时删 Key 重启 Cursor 重配。
- Cursor 只走 OpenAI 协议 → newapi 侧配 OpenAI 兼容渠道（或 OpenAI 兼容的上游）。
- ⚠️ **Cursor 无 Anthropic base URL override**：其内置 Claude 模型只能经 OpenAI 协议转发（若上游是 Claude 原生会触发协议转换、有损）。要 Claude 原生无损，改用 Claude Code 等 Anthropic 协议客户端。

## 11.6 OpenClaw / Hermes / 其他客户端

**核心原则**：先判定协议族，再按 11.4/11.5 配——**不要逐客户端硬编码配置**。

- 若客户端是 **Anthropic 协议**（部分 Cline/Claw 变体、Claude SDK）→ 按 11.4 配 Anthropic 渠道 + `/v1/messages`。
- 若客户端是 **OpenAI 协议**（Cherry Studio/ChatBox/LangChain/OpenAI SDK/openclaw/hermes 多属此类）→ 按 11.5 配 OpenAI 渠道 + `base_url=https://<host>/v1`。
- OpenAI SDK：`OPENAI_BASE_URL=https://<host>/v1`、`OPENAI_API_KEY=<token>`。

> ⚠️ openclaw、hermes 这类名称**非标准、易变**，配置前务必确认它实际发的协议格式（看它请求的 URL 后缀），再选端点与渠道类型。

## 11.7 Gemini 客户端对接

Google AI SDK 走 Gemini 原生协议：
```
base_url = https://<your-newapi-host>           # SDK 自拼 /v1beta/models/...:generateContent
api_key  = <newapi-令牌>                         # ?key= 或 x-goog-api-key，newapi 接受（auth.go:377-389）
```
配 Gemini 渠道（Type=24）走原生直通（定律②）；要字节级再开 PassThrough。

## 11.8 ★GLM-5.2 特殊渠道（改 max_tokens）

GLM-5.2 走 OpenAI 兼容路径（`/v1/chat/completions`）。要改 max_tokens（第 6 章三方案）：

1. **单独建"GLM-5.2 专用"渠道**（Type=1 OpenAI 或 Zhipu，BaseURL 填智谱，`Models=glm-5.2`），**不开 PassThrough**。
2. 该渠道 **ParamOverride**（operations + keep_origin + conditions）：
   ```json
   {"operations":[{"path":"max_tokens","mode":"set","value":4096,"keep_origin":true,
     "conditions":[{"path":"model","mode":"prefix","value":"glm-5.2"}]}]}
   ```
3. 其余模型走**开 PassThrough 的无损渠道**（第 4 章 4.12 路径 A）。
4. 两组渠道用分组/优先级/模型映射隔离，互不影响。

> 这是"无损 + 个别调参"的工程落点：**绝大多数开直通无损，GLM 单独非直通调参**（第 5 章 5.9 互斥结论）。

## 11.9 ★端到端无损验证方法论

配置完，务必验证无损（第 9 章 9.6 详述）：

1. **对账法**：同一问题"直连官方"vs"经 newapi"各跑一遍，对比输出质量 + token 消耗（应一致）。
2. **抓包 diff**（最严格）：mitmproxy 抓"客户端→newapi"和"newapi→上游"请求体，逐字段 diff：
   - 非流式 + PassThrough：**字节级一致**（除 header 鉴权头被渠道密钥替换）。
   - 流式：逐 SSE 事件内容等价（字节因重打包可能不同）。
3. **日志核对**：newapi 日志确认命中的**渠道类型正确**（Claude 客户端命中 Anthropic 渠道）、**模型未被意外映射**、**token 消耗合理**。

发现字段被删/被改 → 查第 5 章 5.8 的 12 项风险点清单，定位规避。

## 11.10 ★关闭破坏纯透传的"智能"功能清单

做无损直通时，确认这些可能"偷偷改请求"的功能已关闭/规避（第 5 章 5.8）：

| 功能 | 配置位置（UI） | 源码 | 无损模式下 |
|---|---|---|---|
| `ChatCompletionsToResponsesPolicy` | 系统设置→模型设置 | `global.go:38` | 确认关闭（默认 false） |
| `FORCE_STREAM_OPTION` | 环境变量 `FORCE_STREAM_OPTION=false` | `compatible_handler.go:54-63` | **默认 true**（流式注入 include_usage）；非直通渠道纯透传须显式关，直通渠道走原始字节可豁免 |
| Thinking/Effort 后缀适配 | （代码层，无 UI 开关） | `claude_handler.go:55-108` | 客户端直接发原生字段，不用后缀模型名 |
| 渠道 SystemPrompt 注入 | 渠道编辑→设置→SystemPrompt | `ChannelSetting.SystemPrompt` | 渠道不配 SystemPrompt |
| ParamOverride | 渠道编辑→参数覆盖 | 渠道 `param_override` | 无损渠道不配；调参走单独非直通渠道 |
| RemoveDisabledFields | 渠道编辑→其他设置 Allow* | `relay_info.go:798-888` | 默认删 service_tier 等；要保留开 Allow*，或开 PassThrough 全保留 |
| 敏感词检查 | 系统设置→运营设置 | — | 按需关 |
| 重试 | 系统设置→运营设置→失败重试次数 | `RetryTimes` | 知悉：一次请求可能跨渠道重试 |
| 锁单渠道对账 | 令牌写 `sk-{token}-{channelId}` | `auth.go:505-513` | **仅管理员**；普通用户用令牌模型限制/分组收敛命中渠道 |

> 最简单的"一键无损"：在该渠道开 `PassThroughBodyEnabled`，上述大部分（Convert/Marshal/RemoveDisabledFields/ParamOverride/SystemPrompt）自动跳过。

## 11.11 故障排查

| 症状 | 排查 |
|---|---|
| 客户端 404 | base_url 多/少了 `/v1`；或端点不存在（如 `/v1/messages/count_tokens`） |
| 客户端 401 | 令牌无效/过期；或鉴权头没被归一化（检查客户端发的头） |
| 质量下降/变笨 | 渠道类型错配（Claude 客户端命中了 OpenAI 渠道→转换有损）；或没开 PassThrough 触发了字段裁剪/注入 |
| max_tokens 改了不生效（GLM） | 该渠道开了 PassThrough（ParamOverride 被跳过）→ GLM 单独建非直通渠道 |
| 响应变慢/超时 | `STREAMING_TIMEOUT`；或重试过多（上游不稳） |
| 渠道自动禁用 | 上游报错触发 AutoBan；调试期关 `AutoBan` |

## 11.12 本章小结（全书收束）

- **无损对接 = 协议匹配端点 + 同类型渠道 + PassThrough 直通**（三定律）。
- **协议族决策树**先判定，再配；base_url 拼接与认证头归一化有规则。
- **Claude Code** → `/v1/messages` + Anthropic 渠道 + PassThrough（count_tokens 404 是已知缺口）。
- **Cursor** → `/v1/chat/completions` + Override Base URL（注意 2025 bug）。
- **GLM-5.2 改 max_tokens** → 单独非直通渠道 + ParamOverride keep_origin（无损与调参分渠道隔离）。
- **验证**：对账 / 抓包 diff / 日志核对；**关闭破坏纯透传的智能功能**或直接开 PassThrough 一键规避。
