## 一、为什么需要这本书

new-api（QuantumNous/new-api）是当下最活跃的开源 AI 网关之一：它能把 OpenAI、Anthropic、Gemini、智谱、DeepSeek、AWS Bedrock 等 40 多家**上游**聚合到一个统一入口，还附带用户管理、**令牌**鉴权、计费**倍率**、负载均衡、日志看板。功能强，迭代快。

但**对一个想认真用它的人（尤其是小白），它并不友好**：

1. **官方文档有关键空白**。最典型的两个：「技术架构」页面是空的占位，「请求透传」只有截图没有文字说明。你想搞懂"请求到底怎么流转""怎样才能做到完全无损"，官方文档帮不上忙。
2. **网上的二手教程普遍过时**。比如几乎所有人都告诉你"部署后用 root / 123456 登录"——但新版 newapi 早已改成**初始化向导**（`controller/setup.go:46`，`model/main.go:57` 的旧函数 `createRootAccountIfNeed` 已是死代码）。又如多数旧教程让 Claude 客户端走 OpenAI 兼容端点做格式转换，而新版已支持**原生 `/v1/messages` 字节级直通**——照旧教程操作，要么卡住，要么白白损失质量。
3. **"无损转发"这件事，大多数人讲不清楚**。市面上大量文章把 newapi 当"格式转换中转站"用（OpenAI ⇄ Claude 互转），却很少有人告诉你：**转换是有损的**，而你其实可以让它做到**字节级无损透传**——前提是你要懂代码层面到底发生了什么。

> 📌 本书中像 `controller/setup.go:46` 这样的写法，是**源码里的位置**（相对仓库根 `D:\newapi\new-api`），全书都用这种写法，便于你核对。完整符号约定见第九节。

这本书就是来填这些坑的。它的立场只有一条：

> **以源码为唯一事实依据。** 任何一个结论，都给你追到 `文件:行号`。文档和源码冲突时，以源码为准，并告诉你差异在哪。

## 二、先认识五个核心词

后面会反复出现这几个词，先用大白话建立直觉（严格定义见[附录 E 术语表](附录E-术语表.md)，后续各章会深入）：

| 词 | 大白话 |
|---|---|
| **上游** | 真正提供模型服务的官方 API，如 OpenAI、Anthropic、智谱。 |
| **渠道（Channel）** | newapi 里"一条指向上游的连接配置"——包含上游地址、密钥、支持的模型等。**本书最核心的配置对象。** |
| **令牌（Token）** | newapi 发给客户端的"调用钥匙"。客户端用它代替上游密钥。 |
| **倍率（Ratio）** | 折算计费的系数（模型倍率、补全倍率、分组倍率）。 |
| **直连** | 客户端不经过 newapi、直接打到官方 API。本书要保证的就是"经过 newapi" 等同于"直连"。 |
| **直通（PassThrough）** | 网关把客户端请求体**一字不改地转发**给上游的模式/开关（渠道级 `PassThroughBodyEnabled` / 全局 `PassThroughRequestEnabled`）。 |

> ⚠️ **"直通"与"直连"一字之差、含义无关**：**直连**=客户端不经网关、直接打官方 API（基准态）；**直通**=网关内部的原样转发模式。本书说"无损直通"指后者。

> 还有一对后面立刻要用：**端点**=客户端访问的 URL 路径（如 `/v1/messages`）；**流式 / 非流式**=大模型 API 的两种返回方式——一次性返回完整结果（非流式）与逐字实时吐出（流式）。这个区别对"能不能字节级无损"至关重要，第六节细讲。

## 三、这本书能帮你做到什么

- **从 0 到 1 真正读懂 new-api**：不是"会点按钮"，而是理解它的分层架构、请求生命周期、每个配置项背后的代码逻辑。
- **搭出一个透明无损转发网关**（核心主线）：让 claude code、cursor、openclaw、hermes 等客户端（这些都是会调用大模型 API 的工具）经 newapi 转发到原生上游，**模型输出质量等同直连官方 API**（精确物理边界见第七节：非流式请求体字节级、流式为事件内容等价、header 鉴权必被覆盖），并在需要时对个别模型（如 GLM-5.2）微调个别参数。
- **避坑**：把那些"会偷偷改变请求、导致质量下降"的环节逐一列出，告诉你怎么关掉、怎么规避。

**本书不讲什么**（划清边界）：不讲 Go 二次开发与插件编写、不逐家讲解 40+ 上游的独有参数（只讲与无损转发相关的差异点）、不深入前端定制；这些请参考官方文档与源码。

## 五、核心主线：透明无损转发

这是贯穿全书、也是第 11 章最终实战的诉求，原始定义是：

> 把 newapi 配置成一个**透明无损转发网关**——原封不动地把客户端发给**原生上游**的请求转发出去，**不做任何兼容转换**；对个别模型（如 GLM-5.2）**微调个别参数**（如 `max_tokens`）。
>
> **铁律：经过 newapi 必须等同直连官方 API——不能有一丁点质量下降。**（在需要时再做主动、可控的微调。）

⚠️ **实现这条主线的关键认知（务必先建立）**：在 newapi 里，"字节级无损直通"与"在网关侧改参数"**在同一渠道内是互斥的**——开了直通，网关就不再动请求体一分一毫；要在网关改 `max_tokens`，就不能开直通。所以正确的做法是**分渠道隔离**：

- **绝大多数模型 / 渠道** → 开 `PassThroughBodyEnabled` 做 100% 字节直通（无损）；
- **个别需要微调的模型（如 GLM-5.2）** → **单独建一个非直通渠道**，用参数覆盖（`ParamOverride`）改 `max_tokens`；
- 两者通过**不同渠道 + 模型映射**隔离，互不影响。

本书第 5 章给互斥的代码证据，第 6 章给 GLM 的三种落地方案。

## 六、无损转发三定律

先把直觉建立起来（代码位置见第 5 章，这里只先建立直觉）：

| 定律 | 大白话 |
|---|---|
| ① **走对入口** | 客户端要用和上游"同一种语言"的接口地址：Claude 客户端走 `/v1/messages`、OpenAI 客户端走 `/v1/chat/completions`、Gemini 客户端走 `/v1beta`。完整端点表见[附录 B](附录B-转发端点表.md)。 |
| ② **上下游说同一种话** | Claude 客户端配 Anthropic 渠道、Gemini 客户端配 Gemini 渠道——别让网关当"翻译"，翻译是有损的。 |
| ③ **开"原样转发"开关** | 极致无损时，开启"请求体直通"（渠道级 `PassThroughBodyEnabled` 或全局 `PassThroughRequestEnabled`），让请求体一字不改地透传。 |

> ⚠️ **定律③的代价**：一旦开启直通，网关侧的**参数覆盖、Claude `max_tokens` 默认注入、系统提示注入**等改写对该渠道一律失效——无损的代价就是不能再在网关动任何参数；要改参数必须另建非直通渠道（见第五节）。（至于"逐字段透传控制"开关也会一并失效，但这是好事——直通已自动保留全部字段，无需再逐字段放行。）

## 七、无损的精确边界（诚实声明，不夸大）

第六节说了"流式 / 非流式"两种返回方式。这里给出全书最重要的诚实声明——**newapi 能做到的无损是有物理边界的**：

| 场景 | 无损等级 |
|---|---|
| **非流式请求体 + 开直通** | **请求体 100% 字节级无损**（原始字节直接转发） |
| **非流式响应体** | **原生 Claude / Gemini**：始终原样字节回写（`relay/channel/claude/relay-claude.go:230-231`、`relay/channel/gemini/relay-gemini-native.go:45`），即使本地补算 usage 也不改字节。**OpenAI 格式 / 跨格式转换路径**：默认字节级回写，但上游没返回用量（本地补算）或开 `ForceFormat` 时会重序列化（`relay/channel/openai/relay-openai.go:236-269`，非字节级） |
| **流式（Claude / Gemini / OpenAI SSE）** | **逐事件解析后重新打包**——事件内容等价，但**非字节级**（无论是否开直通） |
| **请求 header 鉴权** | `Authorization` / `x-api-key` / `x-goog-api-key` 始终被渠道密钥覆盖（**网关鉴权必需，不可避免，也合理**） |

也就是说：**非流式请求体能做到严格字节级无损；流式做到事件内容等价（对客户端解析完全无影响，但严格字节比对会有差异）**。

> 不可被"请求体直通"规避的改写，**至少有三处**：① header 鉴权覆盖（必需）；② 流式 SSE 逐事件重打包；③ **OpenAI 格式**非流式响应在 usage 补算 / `ForceFormat` 时的重序列化（**原生 Claude/Gemini 非流式响应不受此影响，始终字节级回写**）。这是 newapi 的物理上限，本书全程如实标注。全书所有"有损风险点"已汇总于[附录 D · 无损风险点速查表](附录D-无损风险点速查表.md)。

## 八、无损红线（全书总纲）

这是本书最重要的纪律。**每一条涉及请求转发 / 参数改写的配置与操作，都会显式回答三个问题**：

1. **是否无损？** —— 无损 / 语义无损但字节非一致 / 有损。
2. **在哪一层保证？** —— newapi 从最外层的"整包直通"，到逐字段、逐请求头，再到格式转换，分成几层；越靠外越无损（第 5 章详解 L1 整包直通 / L2 字段透传 / L3 header 透传）。
3. **如何验证无损？** —— 给出可执行方法：抓包对比（用工具看实际发出的字节）、字段 diff（逐字段比对请求体）、SSE 帧对比、质量回归（同样的问题跑一遍看答得好不好）。

只要看到书里某个配置说"无损"，你就能追到源码 `文件:行号` 核实；某个功能可能"偷偷改请求"，书里都会标红并给规避方法。
