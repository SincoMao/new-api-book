# 第 8 章 · 计费与成本

> 本章目标：讲清 new-api 的计费逻辑——配额怎么算、倍率怎么配、预扣与结算怎么发生。读完你能配置一组模型的成本核算，并理解计费的安全保护。

---

## 8.1 配额与倍率：计费的基本单位

new-api 用"配额（quota）"作为内部计费单位，所有模型消耗最终折算成配额从用户/令牌余额扣除（〔research/06〕）。

**核心换算**：**1 美元 = 500,000 配额点数**。

**两种计费公式**：
- **按量**（绝大多数聊天/补全模型）：`配额 = (输入token + 输出token × 补全倍率) × 模型倍率 × 分组倍率`
- **按次**（图像/固定价模型）：`配额 = 固定价 × 分组倍率 × 500000`

> 为什么按次要 ×500000？**模型倍率是相对倍率**（基准约 $0.002/1K tokens，乘积天然就是配额点数）；而**按次的"固定价"是美元绝对价**，需 ×`QuotaPerUnit`（默认 500000，即 1 美元=50 万配额，`common/constants.go:22`，可在系统设置改）换算成配额。

其中：
- **补全倍率（completion_ratio）**：输出 token 相对输入 token 的计费系数，通常 >1（生成比读取贵）。
- **模型倍率（model_ratio）**：按模型定价的系数。
- **分组倍率（group_ratio）**：按用户分组的折扣/加价系数。

**倍率参考**（〔research/06〕，供量感，以你实际配置为准）：

| 模型 | 模型倍率 | 补全倍率 |
|---|---|---|
| gpt-4o | 1.25 | 4 |
| gpt-4o-mini | 0.075 | 4 |
| gpt-3.5-turbo | 0.25 | 3 |
| o1 | 7.5 | 4 |

> 未设倍率时：**自用模式**（`SelfUseModeEnabled`，默认单用户自用部署）兜底 37.5（偏高，提醒尽快配置）；**计费模式**（多用户）直接拒绝并报"模型价格未配置"。

## 8.2 模型倍率配置

Web：**系统设置 → 计费倍率**（`/console/setting`）。可按模型设 `model_ratio` 与 `completion_ratio`（`setting/ratio_setting/`）。

- **上游模型与倍率自动同步**：渠道可开启"上游模型更新检测"（`OtherSettings.UpstreamModelUpdate*`，需配 `/v1/models` route），自动拉取上游模型清单与定价（预览新增/变更/删除）。
- **缓存倍率（cache_ratio）**：对支持缓存计费的上游（OpenAI/Azure/DeepSeek 等），命中缓存的输入 token 按更低的 cache_ratio 计费。

## 8.3 分组倍率

分组倍率（`group_ratio`）按用户分组设折扣/加价。例如 `default` 组 1.0、`vip` 组 0.8（8 折）、`premium` 组 1.5。令牌绑定哪个分组，就用哪个分组倍率（第 7 章）。

## 8.4 预扣与结算（含安全保护）

一次请求的计费分两步（`controller/relay.go`）：

1. **预扣（PreConsumeBilling）**：请求转发前，按预估 token 量×倍率**先扣一笔**配额（`controller/relay.go:164`）；**余额不足则直接拒绝、不转发上游**。
2. **结算（SettleBilling，又称 PostConsume）**：上游返回实际 usage 后，按真实 token **多退少补**（差额结算，`controller/relay.go:576`）。

**安全保护（重要，`AGENTS.md` "Billing safety invariants"）**：
- 计费代码**绝不产生负的扣费**（防溢出/负数导致"充值"）。
- 所有用户可控的计费乘数（图像 `n`、视频时长、分辨率/质量比、批次数）都在请求校验时**限定上限**（如 `dto.MaxImageN`、`relaycommon.MaxTaskDurationSeconds`、`maxTokensLimit`），超范围返回 400。⚠️ **这些上限在请求体直通（PassThrough）下仍生效**——计费安全优先于字节透传，属转发前的有意拦截（返回 400，非静默改写）；但 passthrough 字段/`Extra`/metadata/表单可能绕过，适配器读取计费乘数的每条路径都须重复同一上限。
- 配额取整统一走 `common/quota_math.go`（`QuotaFromFloat` 截断、`QuotaRound` 半远离零、`QuotaFromDecimal`），**禁止裸 `int()` 强转**；**饱和**（saturation）边界为 int32（≈±21 亿，配额列是 32 位整数）——结果超此范围时强制卡在边界（不让它回绕成负数变"充值"），并记 `SysError` + 审计。
- **阶梯/动态计费**（`pkg/billingexpr/`，表达式定价）：见该目录的 `expr.md`。

## 8.5 实战：配置一组模型的成本核算

目标：给一个团队配"按真实成本核算"的模型集。

1. **设模型倍率**：系统设置 → 计费倍率，按上游官方定价填 `model_ratio` / `completion_ratio`（如 gpt-4o 1.25/4、deepseek-chat 0.14/0.28 等，具体以上游价格折算）。
2. **设分组倍率**：`default` 组 1.0（原价）；若想给某团队优惠，建 `team-a` 组设 0.9，令牌绑 `team-a`。
3. **开启缓存倍率**（若上游支持）：在模型设置里配 `cache_ratio`，命中缓存自动按低价计。
4. **充值/分配额度**：用户管理 → 给用户/令牌充配额（或用兑换码）。
5. **核对**：日志页查看每次请求的 `配额消耗`、`输入/输出 token`、`倍率`，与上游账单对账。

**验证**：发一条 gpt-4o 请求（输入 1000、输出 500 token），日志应显示消耗 = `(1000 + 500×4) × 1.25 × 1.0 = 3000 × 1.25 = 3750` 配额（3750 ÷ 500000 = $0.0075）。

## 8.6 本章小结

- 配额单位：**1 美元 = 50 万配额**；按量公式 `(输入+输出×补全倍率)×模型倍率×分组倍率`。
- 倍率三层：**补全倍率**（输出/输入）、**模型倍率**（模型定价）、**分组倍率**（分组折扣）。
- 计费两步：**预扣**（按预估）→ **结算**（按真实 usage 差额），多退少补。
- 安全保护：乘数上限校验、统一 `quota_math` 取整、饱和钳制审计、绝不产生负扣费。
- 阶梯/动态计费走 `billingexpr` 表达式系统。
