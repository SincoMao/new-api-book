## 5.2 ★BodyStorage 快照：解析为何不污染直通

这是理解 newapi 无损能力的关键机制（`common/gin.go:36-83`）：

- 客户端请求体在**首次被读取**时，被完整存下一份**原始字节**（BodyStorage）。
- 之后无论"解析校验""计费预估"，还是"直通转发""重试重放"，都用**这同一份快照**，靠 `Seek(0)` 复位重读。

所以——

> **解析作用于 DTO 副本，直通用的是同一份原始字节快照，两者互不污染。** 这就是"网关明明要解析计费，却仍能做到无损直通"的根本原因。直通分支（`compatible_handler.go:107`）取的就是 `GetBodyStorage(c)` 的原始字节，而不是那个被解析、被 DeepCopy、被改写过的 `request` 对象。

## 5.3 原生直通 vs 跨格式转换

### 触发"原生直通"的条件（二选一）
- **全局** `PassThroughRequestEnabled`，默认 `false`（`setting/model_setting/global.go:36,43`）
- **渠道级** `ChannelSettings.PassThroughBodyEnabled`（`dto/channel_settings.go:17`），渠道编辑页按渠道开

判定点（三个 handler 同模式）：
| 格式 | 判定代码 | 直通分支取 body |
|---|---|---|
| OpenAI(Text) | `relay/compatible_handler.go:97` | `ReaderOnly(GetBodyStorage(c))` (:107) |
| Claude | `relay/claude_handler.go:157` | `ReaderOnly(GetBodyStorage(c))` (:163) |
| Gemini | `relay/gemini_handler.go:139` | `ReaderOnly(GetBodyStorage(c))` (:144) |

### 直通分支**绕过**的处理（即无损保证）
1. `ConvertXxxRequest`（格式/字段转换）—— 不调用
2. `common.Marshal(DTO)`（强类型序列化往返）—— 不调用，**不丢任何字段**
3. `RemoveDisabledFields`（删 service_tier 等）—— 内部首行 `if PassThrough… return`（`relay_info.go:799-801`）
4. `ApplyParamOverride`（渠道参数改写）—— 在 else 块内，直通分支不调用（见 5.9）
5. 各 handler 的默认值注入（Claude max_tokens 默认、thinking 适配、SystemPrompt 注入）—— 只改 `request` 副本，直通用原始字节，**不受影响**

### adaptor 层"同格式 identity 直通"（非直通模式下也成立）
即使走转换分支，只要**客户端格式 == 上游渠道格式**，adaptor 的 Convert 也是 identity：
- **OpenAI**：`ConvertOpenAIRequest` 默认 `return request, nil`（`openai/adaptor.go:366`）。仅条件改写：o 系列/GPT-5 把 `max_tokens`→`max_completion_tokens`、OpenRouter 注入 usage/改 reasoning。
- **Claude**：`ConvertClaudeRequest` 对 Anthropic 类型上游直接 `return request, nil`（`claude/adaptor.go:28-30`）。
- **Gemini**：`ConvertGeminiRequest` 对 Gemini 类型上游直接 return，仅轻量规整（首条 role 默认 user、YouTube mime 补全）（`gemini/adaptor.go:26-44`）。

> 所以"原生直通"有两层：① 开 PassThrough = 字节级；② 不开但同协议渠道 = DTO 序列化级 identity（接近无损，但未声明字段可能丢，见 5.5）。

## 5.4 ★PassThrough 三层无损体系

newapi 的无损保证分三层，越靠外越彻底：

| 层级 | 机制 | 粒度 | 默认 | 适用 |
|---|---|---|---|---|
| **L1 字节直通** | `PassThroughRequestEnabled`（全局，`global.go:36`）/ `PassThroughBodyEnabled`（渠道，`channel_settings.go:17`） | 整个请求体 | off | 极致无损，跳过 Convert/Marshal/字段裁剪/ParamOverride |
| **L2 字段透传控制** | `ChannelOtherSettings` 的 `Allow*` 开关（`channel_settings.go:36-56`） | 逐字段 | 各异(默认过滤) | 走 DTO 序列化时，放行 service_tier/inference_geo/speed/safety_identifier/include_obfuscation/store 等非标准字段 |
| **L3 header 透传** | 渠道 `header_override` 的 `pass_headers`/regex（`relay/channel/api_request.go:185-242`） | 逐 header | off | 保留客户端自定义 header（有安全黑名单，不透传凭证） |

- **L1 开启后，L2/L3 的字段级规则对该渠道无需再配**（全部字段已随原始字节保留）。
- **L2 是"反向改写"**：`RemoveDisabledFields`（`relay_info.go:798-887`）默认会**删** service_tier/inference_geo/speed/safety_identifier/stream_options.include_obfuscation（防意外计费/隐私）；要保留就开对应 `Allow*`。
- **L3 规则**：`"*"` 全透传（排除 unsafe）；`"re:<regex>"` 按正则透传；安全黑名单 `passthroughSkipHeaderNamesLower`（`api_request.go:67`）不透传凭证。

## 5.5 参数透传保真（为什么"同格式 identity"仍可能丢字段）

`AGENTS.md` 规定了 DTO 的保真设计规则：
- 请求 DTO 里**可选标量字段必须用指针 + omitempty**（如 `*int`、`*float64`、`*bool`）。
- **保留显式零值**：客户端没传的字段 → `nil`（序列化时省略）；客户端传了 `0`/`false` → 非 nil，照发上游。

这样能精确区分"没传"和"传了零值"。但有一个根本限制：

> **`GeneralOpenAIRequest`（`dto/openai_request.go:29-109`）和 `ClaudeRequest`（`dto/claude.go:206-237`）都是封闭结构，没有通用 `Extra map[string]json.RawMessage` 兜底字段**（只有 `dto/openai_image.go` 的 ImageRequest 有 Extra）。所以非直通路径下，**DTO 未显式声明的字段会在 Unmarshal→Marshal 往返中静默丢失**。

mitigations：项目用 `json.RawMessage` 透传了一批已知新字段（Claude 的 `context_management`/`output_config`/`mcp_servers`/`metadata`/`cache_control`/`speed`/`thinking` 等），主流字段不会丢；但**冷门/全新字段**非直通下不安全。

**结论**：要 100% 字节级保真，唯一保证是 L1（PassThrough）；否则只能靠 RawMessage 覆盖度"近似无损"。

## 5.6 SSE 流式处理（为什么流式做不到字节级）

**流式不存在字节级直通**，无论是否开 PassThrough。

- **OpenAI 流式**（`relay/helper/stream_scanner.go:77` `StreamScannerHandler`）：`bufio.ScanLines` 按行扫上游（:143），**只保留以 `data:` 开头或 `[DONE]` 的行**（:254-264），丢弃 `event:`/`id:`/注释/空行；每个 data 经处理后重打包成 SSE 帧；周期性 `PingData` 注入 `: PING\n\n`（:108-197，可由 `PingIntervalEnabled`/`DisablePing` 关闭）；末帧在 `ShouldIncludeUsage && !containStreamUsage` 时**注入一帧合成的 usage chunk**。
- **Claude 流式**（`relay-claude.go:102-117`）：逐 SSE 事件 Unmarshal→FormatClaudeResponseInfo→重发；非直通时给 `message_delta` 注入补全 usage（直通时 `shouldSkipClaudeMessageDeltaUsagePatch` 跳过，:68-76）。
- **Gemini 流式**（`relay-gemini-native.go:81-93`）：逐事件解析算 usage，但 `helper.StringData` 原样转发 data 文本（内容无损，SSE 帧重建）。

**语义**：流式的**事件内容等价**（客户端解析出的内容一致），但**非字节级**（帧边界、事件拼接、末帧 usage 注入会变）。这是协议层标准行为，对客户端无功能影响，但严格字节比对会有差异。

## 5.7 ★无损的精确边界（诚实声明）

| 场景 | 无损等级 | 代码依据 |
|---|---|---|
| **非流式请求体 + L1 直通** | **100% 字节级无损** | `GetBodyStorage` 原始字节直接转发 |
| **非流式响应（原生 Claude/Gemini）** | **始终字节级回写** | `relay-claude.go:230-231`、`relay-gemini-native.go:45`（即使补算 usage 也不改字节） |
| **非流式响应（OpenAI 格式/转换路径）** | 默认字节级回写；上游未返回用量（本地补算）或开 `ForceFormat` 时重序列化（非字节级） | `relay/channel/openai/relay-openai.go:236-269` |
| **流式（Claude/Gemini/OpenAI SSE）** | **事件内容等价，非字节级** | 逐事件重打包（5.6） |
| **请求 header 鉴权** | 始终被渠道密钥覆盖（网关鉴权必需，不可避免） | adaptor `SetupRequestHeader` |

**不可被"请求体直通"规避的改写，至少三处**：① header 鉴权覆盖（必需）；② 流式 SSE 逐事件重打包；③ OpenAI 格式非流式响应在 usage 补算/`ForceFormat` 时的重序列化（原生 Claude/Gemini 非流式不受此影响）。

> 这就是 newapi 的物理上限：**非流式请求体能做到严格字节级无损；流式做到事件内容等价**。全书如实标注，不夸大。

### 关于 max_tokens 的关键结论
- `maxTokensLimit = math.MaxInt32/2`（`valid_request.go:120`），`exceedsMaxTokensLimit` 只做**上界拒绝**（返回 400），**绝不静默 clamp**。正常值（< ~10.7 亿）原样放行。
- 所以"max_tokens 被网关偷偷改小"在 newapi **不存在**；唯一会主动写 max_tokens 的是第 3 项（Claude 默认注入）和第 8 项（OpenAI 字段改名），均可通过 L1 或显式传值规避。

## 5.9 ★无损直通 ↔ ParamOverride 互斥

**核心矛盾**：三个 handler 的直通分支内**均无** `ApplyParamOverride` 调用（`compatible_handler.go:97-107`、`claude_handler.go:157-163`、`gemini_handler.go:139-144`）。

> 开 L1 = 100% 字节无损，但 ParamOverride（你用来"对个别模型微调 max_tokens"的机制）**完全不生效**；要用 ParamOverride 改 max_tokens，就必须走非直通（承担第 1/2 项风险）。

### 针对"透明无损网关 + 个别模型微调 max_tokens（如 GLM）"的推荐架构
1. **全局/默认渠道开 `PassThroughBodyEnabled`**：让 claude code/cursor 等客户端对绝大多数模型 100% 无损直通。
2. **为需微调的个别模型（如 GLM-5.2）单独建渠道，不开 PassThrough**，配 ParamOverride 改 max_tokens（第 6 章给三种方案）。
3. **代价可控**：GLM 渠道走非直通，但 `GeneralOpenAIRequest` 对 GLM 常用字段（messages/tools/temperature/top_p/stream/max_tokens/reasoning）多用 RawMessage 或指针保留，丢字段风险极低；第 2 项删 service_tier 等（GLM 通常不传，无影响）。

## 5.10 本章小结

- 请求生命周期：中间件鉴权/限流 → Distribute 选渠道 → Relay 主流程 → handler（PassThrough 分叉）→ adaptor 发上游 → 响应回写（流程图见 5.1）。
- **BodyStorage 快照**让"解析计费"与"无损直通"共用一份原始字节、互不污染。
- **PassThrough 三层**：L1 字节直通（最彻底）/ L2 字段透传控制 / L3 header 透传。
- 同协议渠道下 adaptor Convert 是 identity（接近无损），但 DTO 封闭结构是"理论无损"的根本限制——100% 字节级保真唯有 L1。
- **无损边界**：非流式请求体字节级无损；原生 Claude/Gemini 非流式响应字节级回写；OpenAI 非流式响应在 usage 补算/ForceFormat 时重序列化；流式事件内容等价、非字节级。
- **12 项风险点**清单（5.8）+ 规避法（开 L1 一次性绕过大部分）。
- **无损直通 ↔ ParamOverride 互斥**：无损渠道开直通，调参模型走单独非直通渠道。
