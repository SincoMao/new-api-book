# 写作规范（全书统一标准）

> 本文件是《new-api 通透说明书》的写作纲领，主 agent 撰写与审查 agent 审查共同遵循。任何章节都必须符合本规范。

---

## 1. 受众与基调

- **受众**：从完全的小白到能独立运维/二开的进阶用户。默认读者不懂 new-api、可能不熟 Go，但会用命令行和 Docker。
- **基调**：详尽巨著。每章万字级，**原理讲透 + 操作可复现 + 源码 `文件:行号` 佐证 + 避坑清单 + 实战**。不为了短而牺牲"真正懂"。
- **语言**：简体中文。技术术语保留英文原文（如 `PassThrough`、`ParamOverride`、`RelayFormat`）。

## 2. 无损转发红线（最重要，贯穿全书）

这是本书的核心灵魂。**每一条涉及请求转发/参数改写的配置与操作**，都必须显式标注三件事：

1. **是否无损**：无损 / 语义无损但字节非一致 / 有损。
2. **在哪一层保证**：L1 字节直通（PassThrough）/ L2 字段透传控制 / L3 header 透传 / DTO 序列化级 / 协议转换级。
3. **如何验证无损**：给出可执行的验证方法（抓包对比、字段 diff、SSE 帧对比、质量回归）。

**诚实原则**：
- 明确声明无损边界——**非流式请求体 = 字节级无损**；非流式**响应体**（原生 Claude/Gemini）字节级回写，OpenAI 格式在 usage 补算/`ForceFormat` 时重序列化；**流式 = 事件内容等价（非字节级）**。不可被请求体直通规避的改写**至少三处**：header 鉴权覆盖、流式 SSE 重打包、OpenAI 非流式响应重序列化。
- 绝不夸大。绝不为了"显得无损"而隐瞒有损环节。
- 绝不引导小白做出有损配置而不告知。任何"智能"功能（格式转换、参数注入、字段裁剪、SystemPrompt 注入、重试）若可能影响纯透传，必须给出"无损模式下建议关闭/规避"的指引。

## 3. 章节与小节结构模板

### 小节模板
1. **是什么**：一句话定义 + 解决什么问题。
2. **为什么需要**：动机、场景、不这么做的后果。
3. **怎么做**：步骤化、可照做（命令/配置/UI 路径）。
4. **避坑**：常见误配、版本差异、与无损红线的关系。

### 章节模板
- 开头：本章目标 + 你将学会什么 + 前置知识。
- 正文：分小节，遵循小节模板。
- 结尾：**实战**（可复现的端到端操作）+ 本章小结。

## 4. 引用规范

- **源码**：`相对路径:行号`（如 `relay/claude_handler.go:50-53`、`setting/model_setting/global.go:36`）。所有源码结论必须有此引用。
- **研究素材**：标注 `〔research/0X〕`，指向 `D:\newapi\research\0X-*.md`。
- **官方文档**：标注 URL；遇官方空白（技术架构页空、请求透传仅图）明确说明"官方此处空白，本书从源码补齐"。
- **代码块**：配置用 `json`，命令用 `bash`/`powershell`，Go 片段用 `go`。

## 5. 术语规范

- **首次出现给定义**：如「令牌（Token，newapi 中代表一把可调用 API 的钥匙）」。
- **全书统一用词**：统一用"渠道""令牌""分组""倍率""转发""直通/透传"。维护[附录 E 术语表](附录E-术语表.md)。
- **中英对照**：关键配置项给英文标识符（如「请求体直通 `PassThroughBodyEnabled`」）。
- **易混概念区分**：如 `ConvertXxxRequest`（请求侧适配）vs `RemoveDisabledFields`（字段裁剪）；`reasoning/suffix.go`（请求侧推理后缀）vs `relay/reasonmap`（响应侧 finish_reason 映射）。

## 6. 图示规范

- **文字流程图**：用缩进 + 箭头（`│ ▼ ├─`）绘制请求生命周期等。
- **表格**：字段全表、对比表、判定表，带表头。
- **决策树**：协议族判定、渠道选择、无损等级判定等用"条件→分支"文字树。
- **Mermaid**：可选，用于复杂时序图。

## 7. 审查规范（每节质量保证）

每个小节定稿前，用 Workflow 编排**多轮独立子 agent 交叉审查**（用户要求至少 5 轮、无限 token、质量优先）：

| 轮次 | 维度 | 重点 |
|---|---|---|
| 1 | 技术准确性 | 结论是否与源码 `文件:行号` 一致，有无错误/过时 |
| 2 | 无损转发红线 | 是否有损描述、边界是否诚实、有无误导小白 |
| 3 | 小白可读性 | 是否跳跃、术语是否解释、逻辑是否连贯 |
| 4 | 操作可复现性 | 步骤是否完整、能否照做、命令是否准确 |
| 5 | 完整性 | 有无遗漏要点、与全书呼应 |

- **核心章节（第 5/6/11 章）加强**：叠加"对抗性验证"（独立 agent 试图反驳无损结论）+ "完整性批评家"（专门找遗漏）。
- **审查 agent 输入**：`research/01~10` + 源码 + 当前小节草稿；输出结构化修订建议。
- **收敛原则**：连续 1 轮无实质修订即收敛（5 轮基础上按需加码，不为凑数）。审查修订记录留痕。

## 8. 版本对照与演进提示

- 标注源码版本（克隆日期 + 仓库）。配置项随版本演进的，给出版本差异提示（如"新版首次部署用初始化向导，非旧版 root/123456"）。
- 遇官方文档与源码不一致时，**以源码为准**并说明差异。

## 9. 实战可复现性

- 含实战的章节（第 3/4/6/7/11）：步骤可照做、命令可复制、结果可验证。
- 实战末尾给"预期结果"与"验证方法"。
- 涉及无损的实战，必须含"如何确认无损"的验证步骤。
