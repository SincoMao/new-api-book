## 4.1 渠道：透明转发的核心配置对象

回顾第 1 章：**一条渠道 = 一个上游类型 + 上游地址 + 一把 Key + 支持的模型 + 分组 + 调度参数 + 改写规则**。客户端请求最终由某条渠道转发到上游，所以"配渠道"就是"配转发"。结构定义在 `model/channel.go:23-60`。

## 4.4 渠道选择流程（请求怎么命中某渠道）

```
[请求带 model + group 进入 Distribute (distributor.go:32)]
 │
 ▼ 1. 解析 model/group (getModelRequest :252-416，按路径区分 chat/responses/gemini/…)
 ▼ 2. 令牌指定渠道? (sk-{token}-{channelId}，仅管理员) ──是→ 直接用
 ▼ 3. 校验令牌模型限制 → 算 usingGroup
 │      · Group=auto 是特殊聚合组：GetUserAutoGroup (service/group.go:46)
 │        展开为「管理员配置的自动分组 ∩ 用户可用分组」，支持跨组重试
 ▼ 4. 渠道亲和 (GetPreferredChannelByAffinity :104-132)
 │      · 用户+模型+组最近成功过的渠道，仍可用 → 优先复用
 │      · AdvancedCustom 渠道还要 channelSupportsRequestPath 匹配路径 (:175-184)
 ▼ 5. 否则 CacheGetRandomSatisfiedChannel(内存) 或 model.GetChannel(DB)
 ▼ 6. 加权随机 (model.GetChannel ability.go:108-147)
 │      · 取 (group,model) 下 MAX(priority) 集合；重试时按 priority 降序逐级降级 (:63-91)
 │      · AdvancedCustom 额外 filterAbilitiesByRequestPathAndModel (:154-194)

        注入 ChannelId/Type/Setting/OtherSettings/ParamOverride/HeaderOverride/

```

> "笛卡尔积"= 每个模型 × 每个分组，两两组合各生成一条 ability 记录（`AddAbilities` `ability.go:196-311`）。

## 4.5 改写规则：请求侧三件套 + 响应侧状态码

**请求侧三件套**（都在 Convert→Marshal 之后、发上游之前应用）：
- `ModelMapping`（:42）：Convert 之前换模型名。
- `ParamOverride`（:50）：序列化后用 sjson 改任意 JSON 路径 + 请求头（第 6 章）。
- `HeaderOverride`（:51）：改上游请求头。

**响应侧**：
- `StatusCodeMapping`（:44）：把上游非 200 的 HTTP 状态码按 JSON（如 `{"429":500}`）重映射后返回客户端（`service/error.go:133` ResetStatusCode）。⚠️ 它作用于**错误响应状态码**，与请求侧改写不同，**不受 PassThrough 影响**。

### ⚠️ PassThrough 下谁失效、谁仍生效
开启请求体直通（`PassThroughBodyEnabled`）后：
- **失效**：`ModelMapping` / `ParamOverride` / `RemoveDisabledFields`（它们改 body）。
- **仍生效**：`HeaderOverride`（改 header 不改 body，`relay/channel/api_request.go:319-323` 在 SetupRequestHeader 之后应用）；`StatusCodeMapping`（响应侧）。
- 若 HeaderOverride 内嵌于 ParamOverride 的 `set_header`/`pass_headers` operation，则随 ParamOverride 一并失效。

## 4.6 ★无损策略三档（全书核心决策框架）

配置渠道时，先按下表选定无损档位（这是贯穿全书的决策依据）：

| 档位 | 触发条件 | 无损级别 | 改写是否生效 | 典型场景 |
|---|---|---|---|---|
| **(a) 默认结构化转换** | 内置类型，**不开** PassThrough | **有损**（DTO 序列化往返，未声明字段丢失、字段裁剪、可能注入默认值） | 全部生效 | 需要网关改写参数/字段时 |
| **(b) PassThrough 字节直通** | 内置类型，开 `PassThroughBodyEnabled`（渠道）/ `PassThroughRequestEnabled`（全局） | **请求体字节级无损**（响应：非流式字节级/流式事件等价） | body 改写全失效（header 改写仍生效） | ★绝大多数模型/客户端的首选 |
| **(c) AdvancedCustom converter=none** | 类型 58，`Converter=none`（不开 PassThrough） | **语义无损但字节非一致**（仍经结构化序列化） | 生效（结构化路径内） | 自定义 base_url 接任意上游、跨协议 |

> 要在 (c) 上达到 (b) 的字节级：在 converter=none 的 route 所在渠道**再开 `PassThroughBodyEnabled`**（仅 converter=none 的 route 允许，跨协议 route 不允许，`advancedcustom/adaptor.go:272-274`）。

## 4.7 ★AdvancedCustom 渠道（类型 58）——任意上游透明直通

newapi"接任意自定义上游"的官方答案。用**路由表 + 协议转换器 + 灵活鉴权**通用化（老式 Custom 见 4.8）。

### 配置结构（DTO 在 `dto/channel_settings.go`，存在渠道 `OtherSettings` 列）
- `AdvancedCustomConfig`（:82-84）：`{ Routes []AdvancedCustomRoute }`。
- `AdvancedCustomRoute`（:86-92）：`IncomingPath`、`UpstreamPath`、`Converter`、`Models []string`、`Auth`。

⚠️ **JSON 字段名是 `advanced_routes`，不是 `routes`**（`dto/channel_settings.go:83` 的 tag 是 `json:"advanced_routes,omitempty"`）。配置写 JSON 时用 `advanced_routes`，照 Go 字段名 `Routes` 当 key 会静默失败（Validate 报 "requires at least one route"）。

### Converter（8 种，:65-74）
> 命名读作**入口协议_to_上游协议**（左=客户端发来的格式，右=上游要的格式）。
- **`none`** = 不改协议 = **原生格式结构化直通**（语义无损但字节非一致，仍经序列化；要字节级需再开 PassThrough）。
- `anthropic_messages_to_openai_chat_completions` / 反向
- `openai_chat_completions_to_openai_responses` / 反向
- `openai_responses_to_gemini_generate_content`
- `openai_chat_completions_to_gemini_generate_content`
- `gemini_generate_content_to_openai_chat_completions`

> `Converter=none` 避免了"跨协议转换"这层损失，但请求体仍经结构化序列化（语义无损、字节非一致）。要字节级无损，在该 route 渠道再开 `PassThroughBodyEnabled`。

### Auth（`AdvancedCustomRouteAuth` :94-98，3 种）
- **未配置（Auth 为 nil）** → 默认加 `Authorization: Bearer {api_key}`。
- `type=none` → **显式不加任何鉴权头**（注意：与 nil 不同！用于上游无需鉴权、或已用 query 鉴权不再加头）。
- `type=header` → 自定义头名 + 模板（`Value` 支持 `{api_key}` 占位）。⚠️ 每条 route 的 Auth 只支持一个自定义头。
- `type=query` → 拼到 URL query 参数。

### adapter 行为（`relay/channel/advancedcustom/adaptor.go`）
- 内部组合 openai/claude/gemini 三 adapter（:30-39），按 converter 委托；**AdvancedCustom 无独立 handler**，复用对应 RelayFormat 的 handler（故 `PassThroughBodyEnabled` 由该 handler 统一识别，无需单独配）。
- `resolve`（:350-378）：`MatchPathForModel(请求路径, 模型)` 选 route。
- `GetRequestURL`（:189 → `buildRouteURL` :394）：
  - **`UpstreamPath` 的 `{model}`** 替换为上游模型名（`applyUpstreamPathTemplate` :465-470）。
  - **`IncomingPath` 的 `{model}`** 用于**路径模式匹配**（非替换，`channel_settings.go:285-300`），支持 `:generateContent ↔ :streamGenerateContent` 等价匹配。
  - 相对 UpstreamPath 拼到 `ChannelBaseUrl`；realtime 自动 http→ws(s)。
  - ⚠️ "Gemini 流式自动改 `:streamGenerateContent`+`alt=sse`"**仅在两个 OpenAI→Gemini 跨协议 converter 下触发**（`shouldUseGeminiStreamURL` :472-477）；**converter=none 的原生 Gemini route 不会自动改上游 URL**——需分别为 `:generateContent` 与 `:streamGenerateContent` 配 UpstreamPath，或直接写 `:streamGenerateContent`。
  - Claude 原生 route（converter=none）的 `anthropic-version` 头由 adapter 自动注入（默认 `2023-06-01`，或透传客户端值，:490-507），**无需手动配**。
- **强制约束 + 失败模式**（:272-274）：`converter != none` 的 route 不能配 pass-through body。⚠️ **陷阱**：渠道级 `PassThroughBodyEnabled` 一开即对该渠道**所有 route** 生效；若渠道里混了 converter!=none 的 route，请求命中那些 route 时**运行期硬报错**（`converter routes cannot be used with pass-through request body`），而 `Validate()` 配置期**不会拦**。→ 避坑：混用 converter=none 与跨协议 converter 的渠道**不要开 PassThrough**，或拆成两条独立渠道。

## 4.8 Custom(8) vs AdvancedCustom(58)

| 维度 | Custom(8) | AdvancedCustom(58) |
|---|---|---|
| 协议格式 | 仅 OpenAI | OpenAI/Claude/Gemini 任一 + 跨协议转换 |
| URL 拼接 | 整个 BaseURL 当请求 URL | BaseURL + 路由表 UpstreamPath |
| 占位符 | BaseURL 里 `{model}` 替换 | UpstreamPath `{model}` 替换、IncomingPath `{model}` 匹配、Auth `{api_key}` |
| 鉴权 | 单一 | 3 种（none/header/query）+ 模板 |
| 路径/模型路由 | 无 | 路由表（按路径+模型匹配） |
| `/v1/models` 发现 | 无 | 支持（需配特殊 route） |
| 跨协议转换 | 无 | 8 种 converter |
| PassThrough | — | 仅 converter=none route 允许 |
| **推荐** | 仅历史兼容 | **新场景一律用 58** |

## 4.9 各适配器差异

所有 adapter 实现 `Adaptor` 接口（`relay/channel/adapter.go:15-32`）。差异主要在三处：`GetRequestURL`（拼上游 URL）、`ConvertXxxRequest`（统一请求→上游格式）、`SetupRequestHeader`（鉴权头：OpenAI 系 `Authorization: Bearer`；Claude `x-api-key`+`anthropic-version`；AWS AKSK；Vertex OAuth；Gemini `x-goog-api-key`）。

> 选定某厂商 adapter 后，**默认**必经其 Convert（结构化解析→重序列化），非纯字节透传；**一旦开启 PassThroughBodyEnabled，则跳过 Convert，原始字节直传**（这才是字节级无损）。适配器在整体转发管线中的位置见[第 2 章](02-技术架构全景.md)。

## 4.10 自动禁用/启用、多 Key、标签（`service/channel.go`）

- **自动禁用**（`ShouldDisableChannel` :45）：全局开关关闭则不禁；渠道级错误必禁；状态码命中禁；错误消息关键词匹配（多模式快速匹配）禁。`DisableChannel`（:19）要求 `AutoBan` 开启，并同步 ability `enabled=false`。
- **自动启用**（`ShouldEnableChannel` :67）：全局开启 + 请求成功 + 当前自动禁用 → 自动恢复。
- **多 Key**（`ChannelInfo` `model/channel.go:62-70`，7 个子字段）：`IsMultiKey`、`MultiKeySize`、`MultiKeyStatusList`（每 key 启停状态）、`MultiKeyDisabledReason`/`MultiKeyDisabledTime`、`MultiKeyPollingIndex`（轮询游标，线程安全 `GetChannelPollingLock`）、`MultiKeyMode`（random/polling）。单 Key 失败只禁该 Key，全禁才禁渠道。进入多 Key：新建时 `Mode=multi_to_single`、编辑时 `KeyMode=append/replace`。
- **标签**：按标签批量编辑（`model.EditChannelByTag` `model/channel.go:805`）。

> 调试期可关 `AutoBan` 或全局 `AutomaticDisableChannelEnabled`，避免渠道被频繁自动禁用影响排错。

## 4.11 渠道 CRUD 与权限/审计（`controller/channel.go`）

- **三级权限**（`authz`）：
  - `ChannelSensitiveWrite`：创建 `AddChannel`、删除 `DeleteChannel`/`DeleteChannelBatch`/`DeleteDisabledChannel`、查看密钥 `GetChannelKey`（需额外安全验证）。
  - `ChannelWrite`：更新 `UpdateChannel`、按标签编辑 `EditTagChannels`、批量打标签。
  - `ChannelOperate`：状态/测试/余额/修复/拉取上游模型。
- **AddChannel 三种 Mode**（:608）：`single`（单 Key）、`multi_to_single`（多 Key 合并到一个渠道，启用轮询/随机）、`batch`（每行 Key 建一个独立渠道）。
- **UpdateChannel**（:941）：`KeyMode=append/replace`；保留原 ChannelInfo，重算 MultiKeySize。
- **validateChannel**（:474）：校验 proxy、OtherSettings JSON、advanced_custom 必填与合法性、Vertex region JSON 须含 `default`、Codex key 须含 `access_token`/`account_id`。
- **审计**：所有写操作 `recordManageAudit`；敏感写受 `ChannelSensitiveWrite` 保护。

## 4.12 ★实战：配置"原生透明直通"渠道（含完整 JSON）

### 路径 A：内置类型 + PassThrough（字节级无损，推荐）
以 Anthropic 渠道（给 claude code 用）为例。Web：**渠道编辑页 → 填基本信息 → 高级设置 → 打开"请求体直通"开关**。

| 字段 | 值 |
|---|---|
| Type | 14（Anthropic） |
| Key | `sk-ant-...` |
| BaseURL | 留空（用官方） |
| Models | `claude-sonnet-4-5,claude-opus-4-8,...` |
| Group | `default` |
| Setting（`setting` 列） | `{"pass_through_body_enabled": true}` |

**无损性**：claude code 打 `/v1/messages` → 命中 Anthropic 渠道 → Claude 协议原生 + PassThrough → **请求体字节级无损**（响应：非流式字节级，流式事件内容等价，见[第 5 章](05-转发核心机制-透明无损原理.md)）。客户端协议↔端点对照见第 11 章。

### 路径 B：AdvancedCustom（converter=none，接任意上游）
Web：**渠道编辑页 → Type 选"高级自定义" → 其他设置(JSON) 编辑框**填入 `OtherSettings`：

```json
{
  "advanced_custom": {
    "advanced_routes": [
      {
        "incoming_path": "/v1/chat/completions",
        "upstream_path": "/v1/chat/completions",
        "converter": "none",
        "models": ["gpt-4o", "gpt-4o-mini"],
        "auth": {"type": "header", "name": "Authorization", "value": "Bearer {api_key}"}
      },
      {
        "incoming_path": "/v1/messages",
        "upstream_path": "/v1/messages",
        "converter": "none",
        "models": ["claude-sonnet-4-5"],
        "auth": {"type": "header", "name": "x-api-key", "value": "{api_key}"}
      }
    ]
  }
}
```
- BaseURL 填上游根地址（如 `https://your-upstream.com`）。
- Claude route 的 `anthropic-version` 由 adapter 自动注入，无需手配。
- **无损性**：`converter=none` = 语义无损但字节非一致（结构化序列化级）。**要字节级**：在该渠道 Setting 再开 `pass_through_body_enabled: true`（⚠️ 仅当所有 route 都是 converter=none 时才能开；混入跨协议 route 会在请求期硬报错，见 4.7）。
- **响应侧**：无论是否开 PassThrough，响应仍走 adapter DoResponse（usage 统计、SSE 重打包），属"事件内容等价、非字节级"（第 5 章）。

**验证无损**：用抓包工具（如 mitmproxy）对比"客户端→newapi"与"newapi→上游"的请求体；或逐字段 diff（第 11 章给完整方法论）。

### 避坑清单
- base_url 必须含 scheme（http/https）；AdvancedCustom 相对 UpstreamPath 要求 BaseURL 完整；realtime 自动转 ws/wss。
- 默认 BaseURL 为空的类型（3/8/33/41/58）必须手填。
- **透传 vs 改写**：开 PassThrough 后 ModelMapping/ParamOverride/RemoveDisabledFields 失效（HeaderOverride 仍生效）；要改参数就别开透通。
- AdvancedCustom 混用 converter=none 与跨协议 converter 的渠道**不要开 PassThrough**（运行期硬报错）。
- `max_tokens` 上限：`valid_request.go` 的 `maxTokensLimit` 对每种格式强校验（第 6 章）。
- 自动禁用：默认 `AutoBan=1`，调试期可关。

## 4.13 本章小结

- 渠道 = 类型 + 地址 + 密钥 + 能力 + 调度 + 改写（字段表见 4.2）。三个设置位置分清：`Setting`(单数)/`OtherSettings`(复数)/改写三列。
- **无损三档**：(a) 默认结构化转换（有损）/ (b) PassThrough 字节直通（请求体字节级无损）/ (c) AdvancedCustom converter=none（语义无损但字节非一致）。
- 渠道选择：ability 表 → 优先级 → 权重加权随机（+10 保底）→ AdvancedCustom 路径过滤 → 亲和（流程图见 4.4）。
- **AdvancedCustom（58）= 任意上游透明直通的官方答案**；JSON 字段是 `advanced_routes`；`converter=none` 是原生格式结构化直通，要字节级再开 PassThrough（仅 converter=none route 允许）。
- CRUD 三级权限、AddChannel 三 Mode、审计（4.11）；编程包预设地址 ChannelSpecialBases（4.3）。
