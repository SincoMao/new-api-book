# 第 3 章 · 部署与运维

> 本章目标：手把手把 new-api 稳稳跑起来，并掌握日常运维（升级、备份、多节点、安全）。含完整实战。
>
> ⚠️ **先记一个避坑**：新版 newapi 首次部署**已不再用 root / 123456**，而是**初始化向导**。如果你照着网上旧教程找默认密码，会找不到——见 3.3。

---

## 3.1 部署方式选型

| 方式 | 适合 | 难度 |
|---|---|---|
| **Docker Compose（推荐）** | 生产环境、需要 MySQL/PG+Redis | ★★ |
| Docker 单容器 | 个人、小规模、用 SQLite | ★ |
| 1Panel 面板 | 不熟命令行 | ★ |
| 宝塔面板 | 不熟命令行 | ★ |
| 集群（主从） | 大规模、高可用 | ★★★★ |
| 本地开发 | 二开、贡献代码 | ★★★ |

本章重点讲 **Docker Compose**（生产推荐）和**单容器**（最快上手），其余简述。

## 3.2 实战：Docker Compose 生产部署

new-api 官方 `docker-compose.yml` 默认编排了 **new-api + PostgreSQL + Redis** 三个服务。下面是完整步骤。

### 步骤 1：准备服务器与 Docker
- 64 位系统（amd64 / arm64），装好 Docker 与 Docker Compose。
- 开放端口 3000（或你映射的端口）。

### 步骤 2：获取 docker-compose.yml
你可以直接克隆官方仓库（`git clone https://github.com/QuantumNous/new-api.git`），或自己新建 `docker-compose.yml`。下面是官方默认配置的核心（**精简版，省略了部分注释与 mysql/clickhouse 可选项；生产以仓库内 `docker-compose.yml` 为准**）：

```yaml
services:
  new-api:
    image: calciumion/new-api:latest
    container_name: new-api
    restart: always
    command: --log-dir /app/logs
    ports:
      - "3000:3000"
    volumes:
      - ./data:/data        # 数据库(SQLite时)、配置等
      - ./logs:/app/logs    # 日志
    environment:
      - SQL_DSN=postgresql://root:123456@postgres:5432/new-api   # ⚠️ 生产必改密码
      - REDIS_CONN_STRING=redis://:123456@redis:6379              # ⚠️ 生产必改密码
      - TZ=Asia/Shanghai
      - ERROR_LOG_ENABLED=true
      - BATCH_UPDATE_ENABLED=true
      - NODE_NAME=new-api-node-1
      # - SESSION_SECRET=random_string   # ⚠️ 多机部署必须改成固定随机串
    depends_on:
      - redis
      - postgres
    healthcheck:
      test: ["CMD-SHELL", "wget -q -O - http://localhost:3000/api/status | grep -o '\"success\":\\s*true' || exit 1"]
      interval: 30s
      timeout: 10s
      retries: 3

  redis:
    image: redis:latest
    restart: always
    command: ["redis-server", "--requirepass", "123456"]   # ⚠️ 改密码

  postgres:
    image: postgres:15
    restart: always
    environment:
      POSTGRES_USER: root
      POSTGRES_PASSWORD: 123456        # ⚠️ 改密码
      POSTGRES_DB: new-api
    volumes:
      - pg_data:/var/lib/postgresql/data
```

### 步骤 3：修改默认密码（生产必做）
把 `SQL_DSN`、`REDIS_CONN_STRING`、`POSTGRES_PASSWORD`、redis `requirepass` 里的 `123456` **全部改成强密码**，且 new-api 用的密码要与 postgres/redis 里设的一致。

### 步骤 4：启动
```bash
docker compose up -d
```

### 步骤 5：访问与初始化
- 浏览器打开 `http://<服务器IP>:3000`。
- **首次访问会进入初始化向导**（见 3.3），按引导创建管理员账号。
- 健康检查：`curl http://localhost:3000/api/status` 应返回 `"success": true`。

### 想换 MySQL？
官方 yml 注释里写了：注释掉 postgres 服务和 PG 的 `SQL_DSN` 行，取消注释 mysql 服务与 `SQL_DSN=root:123456@tcp(mysql:3306)/new-api` 行即可。

### 想要独立日志库（ClickHouse）？
取消注释 `LOG_SQL_DSN=clickhouse://...` 与 clickhouse 服务，并设 `LOG_SQL_CLICKHOUSE_TTL_DAYS=30` 控制留存天数。

## 3.3 首次启动：初始化向导（★重要避坑）

⚠️ **新版 newapi 不再有默认 root / 123456**。`model/main.go:57` 的 `createRootAccountIfNeed` 是**死代码**（全仓无调用方，函数体内还硬编码着旧的 root/123456，但根本不会执行）。

现行的首次初始化流程：

1. 启动时 `CheckSetup()` 查 `setups` 表（`controller/setup.go`）。
2. 前端检测到 `setup=false`，展示**初始化向导**页面。
3. 你在向导里填管理员**用户名（≤12 字符）**和**密码（≥8 字符）**，提交 `POST /api/setup`（`controller/setup.go:46`）创建管理员。向导还会让你勾选两项：
   - **自用模式（SelfUseModeEnabled）**：仅供自己/内部使用，关闭公开注册等；个人与小团队推荐勾。
   - **演示站点（DemoSiteEnabled）**：开启演示数据，生产环境**不要**勾。
4. 之后用这个账号登录。

> 避坑：看到登录页却没有任何默认密码，说明你撞上了新版——回到首访初始化向导创建管理员。若误操作跳过向导：**先备份数据库**，确认无管理员用户后删除 `setups` 表当条记录即可重新触发向导（**切勿**"重置数据库"，会丢数据）。

## 3.4 数据库选型与切换

由 `SQL_DSN` 环境变量决定（`model/main.go:127-179` 的 `chooseDB` 按前缀判定）：

| SQL_DSN 形式 | 数据库 | 说明 |
|---|---|---|
| 留空 / `local` | **SQLite**（默认） | 数据库文件 `/data/one-api.db`（`common/database.go:44`），即映射的 `./data` 目录；仅适合测试/个人 |
| `postgresql://...` | PostgreSQL | 生产推荐 |
| `user:pass@tcp(host:3306)/db` | MySQL（自动补 parseTime） | 兼容；启动校验中文字符集，不达标 panic |

| 场景 | 推荐 |
|---|---|
| 个人尝鲜 | SQLite（单容器最快） |
| 生产 / 多节点 | PostgreSQL + Redis |
| 从 one-api 迁移 | new-api 兼容 one-api 数据库，可直连原有库 |

日志库可独立：`LOG_SQL_DSN` 指向另一个库（如 ClickHouse），仅存日志，配 TTL 自动清理。

## 3.5 Redis 缓存（可选，何时必备）

- `REDIS_CONN_STRING` 留空 → `RedisEnabled=false`，程序照常跑（令牌缓存、限流回退到数据库/内存）。**单机可不配。**
- **多节点 / 高并发必备**：共享 Redis 才能跨节点共享限流额度、令牌缓存。
- 开启 Redis 会强制 `MemoryCacheEnabled=true`。
- 多节点共享 Redis 时，所有节点必须设相同的 `CRYPTO_SECRET`（缓存键 HMAC 密钥，默认跟随 `SESSION_SECRET`），否则缓存键对不上。

## 3.6 环境变量全集（8 大类）

> 主要入口在 `common/init.go` 与 `common/constants.go`。下面按类列出高频项；完整说明见[附录 A · 环境变量表](附录A-环境变量表.md)。

**① 数据库**
- `SQL_DSN`：主库连接串（决定库类型，见 3.4）
- `LOG_SQL_DSN`：独立日志库（可选）
- `LOG_SQL_CLICKHOUSE_TTL_DAYS`：ClickHouse 日志留存天数（0=不清）

**② 缓存**
- `REDIS_CONN_STRING`：Redis 连接串（可选）
- `MEMORY_CACHE_ENABLED`：内存缓存（开 Redis 时强制开）

**③ 服务**
- `TZ`：时区（如 `Asia/Shanghai`）
- `NODE_NAME`：节点名（审计日志标识）
- `NODE_TYPE`：`slave` 时**跳过数据库迁移**，且 DB 租约型系统任务由 master 排他执行（配置/渠道缓存等周期同步在各节点仍运行）
- `FRONTEND_BASE_URL`：前端分离部署地址（主节点忽略）

**④ 安全（生产关键）**
- `SESSION_SECRET`：鉴权签名密钥；**多节点必须全节点一致**；不可设为 `random_string`
- `CRYPTO_SECRET`：**缓存键 HMAC 密钥**（`common/crypto.go:17`，默认跟随 `SESSION_SECRET`）；共享 Redis 时多节点必须一致，否则缓存键对不上（仅导致缓存未命中→回库重取，**不会**致历史数据不可读）
- `SESSION_COOKIE_SECURE` + `SESSION_COOKIE_TRUSTED_URL`：HTTPS 场景启用 Secure Cookie 与严格 Origin 校验
- `TRUSTED_PROXIES`：反代场景信任的代理 IP/CIDR；`none`=严格模式；留空=信任回环+RFC1918（带告警）

**⑤ 限流 / 会话**
- `USER_SESSION_ACTIVE_LIMIT`(50)、`USER_SESSION_ISSUANCE_LIMIT`(100)、`USER_SESSION_ISSUANCE_WINDOW_SECONDS`(86400)、`USER_SESSION_REVOKED_RETENTION_DAYS`(7)、`USER_SESSION_HOURLY_ALERT_THRESHOLD`(5000)

**⑥ 转发超时与请求体限制**
- `STREAMING_TIMEOUT`(300)：流式无响应超时（秒；⚠️ 官方 `docker-compose.yml` 注释里的 120s 已过时，代码实际默认 300，`common/init.go:177`）
- `STREAM_SCANNER_MAX_BUFFER_MB`(**128**)：流式单行最大缓冲 MB（4K 图片 base64 等需调大；`common/init.go:180`）
- `MAX_REQUEST_BODY_MB`(**128**)：请求体上限（解压后计，超限 413；`common/init.go:182`）
- ⚠️ `RELAY_TIMEOUT`：**默认 0（不限制）= 官方建议值**；仅在设为正数时才触发整体 HTTP 超时（`service/http_client.go:104-106`）——此时上游已计费但本地超时未计费，可能亏损，故建议保持默认 0〔research/06〕

**⑦ 特性**
- `FORCE_STREAM_OPTION`(true)：**仅流式请求**触发；对支持 StreamOptions 的渠道**覆盖** `stream_options.include_usage=true`（为拿用量；属请求体字段注入/覆盖，**有损**；无损模式与规避详见第 6 章）
- `BATCH_UPDATE_ENABLED`：批量更新（性能）
- `ERROR_LOG_ENABLED`：错误日志

**⑧ 监控**
- `PYROSCOPE_URL` / `PYROSCOPE_APP_NAME` 等：Pyroscope 性能分析

## 3.7 升级与备份

**升级**：
1. 先备份（见下）。
2. 多节点：先升 slave（`NODE_TYPE=slave`），再升 master。
3. 换新镜像重启：`docker compose pull && docker compose up -d`。
4. 主节点启动时自动 `AutoMigrate`（跨版本一般无需手动 SQL）。

**备份（务必）**：
- 数据库：定期 dump（PG 用 `pg_dump`，MySQL 用 `mysqldump`）。
- `/data` 目录（SQLite 数据、配置、上传文件）。
- **`CRYPTO_SECRET`**：缓存键 HMAC 密钥（默认跟随 `SESSION_SECRET`）。换了只会让旧缓存键失效（触发缓存重建），**不会**致数据不可读；多节点共享 Redis 时务必备份并保持全节点一致。

## 3.8 多节点集群与安全三件套

**集群（主从）要点**：
- 所有节点共享同一个 PostgreSQL 主库。
- `SESSION_SECRET` 全节点相同（否则 Access Token/Refresh 跨节点校验失败）。
- 共享 Redis 则 `CRYPTO_SECRET` 也须相同。
- 从节点设 `NODE_TYPE=slave`（跳过迁移；DB 租约型系统任务由 master 排他执行）。
- 前面用 Nginx 按权重负载均衡。

**安全三件套（生产必做）**：
1. **改默认密码**（数据库、Redis、管理员）。
2. **`SESSION_SECRET` 固定且保密**（多节点一致）。
3. **`CRYPTO_SECRET` 多节点一致**（缓存键 HMAC 密钥，非加密密钥；共享 Redis 时必须相同）。
- 反代场景配 `TRUSTED_PROXIES`；HTTPS 场景配 `SESSION_COOKIE_SECURE` + `SESSION_COOKIE_TRUSTED_URL`。

**启动失败排查（小白自救）**：用 `docker compose logs -f new-api` 看后端日志，常见三类：
- **密码不一致**：`SQL_DSN` / `POSTGRES_PASSWORD` / redis `requirepass` 三处对不上 → 改齐后重启。
- **MySQL 字符集不达标**：启动直接 panic → 把库字符集改为 utf8mb4。
- **3000 端口被占**：换映射端口（如 `-p 3001:3000`）。

## 3.9 其他部署方式（简述）

- **Docker 单容器（SQLite，最快）**：
  ```bash
  docker run --name new-api -d --restart always \
    -p 3000:3000 -e TZ=Asia/Shanghai -v ./data:/data \
    calciumion/new-api:latest
  ```
- **1Panel / 宝塔**：应用商店搜 "New-API"，一键安装，勾选端口外部访问、映射 `/data`、配 `SESSION_SECRET`。
- **本地开发**：后端 Go（`go run main.go`），前端 `cd web && bun install && bun run dev`，`.env` 配 DSN。

## 3.10 本章小结与实战验证

- 生产推荐 **Docker Compose + PostgreSQL + Redis**，镜像 `calciumion/new-api:latest`，端口 3000。
- ⚠️ 首次部署走**初始化向导**，没有 root/123456。
- 数据库由 `SQL_DSN` 前缀决定（SQLite/PG/MySQL）；日志库可独立。
- 生产必做安全三件套：改密码、固定 `SESSION_SECRET`、多节点 `CRYPTO_SECRET` 一致（缓存键 HMAC 密钥，非加密密钥）。
- 升级先备份、先 slave 后 master；换镜像重启自动迁移。

**实战验证**：
1. `docker compose up -d` 后，`curl http://localhost:3000/api/status` 返回 `"success": true`。
2. 浏览器访问 `:3000`，完成初始化向导，能用创建的管理员账号登录。
3. 在"渠道"里加一个测试渠道（第 4 章），在"操练场"发一条消息能收到回复——说明部署成功。
